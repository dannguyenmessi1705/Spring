# Spring GraphQL
## 1. Giới thiệu
Spring GraphQL là một phần mở rộng của Spring Framework giúp xây dựng các dịch vụ GraphQL một cách dễ dàng và hiệu quả. Nó cung cấp các công cụ và tiện ích để xử lý các truy vấn GraphQL, định nghĩa schema, và tích hợp với các thành phần khác của Spring

GraphQL hỗ trợ cả lập trình đồng bộ và phản ứng, cho phép bạn xây dựng các ứng dụng web hiện đại với hiệu suất cao.

GraphQL là một ngôn ngữ truy vấn API mạnh mẽ, cho phép khách hàng yêu cầu chính xác những gì họ cần từ máy chủ. Điều này giúp giảm thiểu việc truyền tải dữ liệu không cần thiết và cải thiện hiệu suất của ứng dụng.

## 2. GraphQL Types
GraphQL định nghĩa một số loại dữ liệu cơ bản, bao gồm:
### 2.1. Scalar Types
Các loại dữ liệu nguyên thủy bao gồm:
- **Int**: Số nguyên 32-bit có dấu.
- **Float**: Số dấu phẩy động 64-bit.
- **String**: Chuỗi ký tự UTF-8.
- **Boolean**: Giá trị đúng hoặc sai.
- **ID**: Một định danh duy nhất, thường được sử dụng để tham chiếu đến các đối tượng. ID được biểu diễn dưới dạng chuỗi, bất kể giá trị thực tế là gì cũng sẽ được serialize thành chuỗi.

Ví dụ:
```graphql
type User {
    id: ID!
    name: String!
    age: Int
    isActive: Boolean!
}
```
> Lưu ý: Dấu chấm than (!) sau kiểu dữ liệu biểu thị rằng trường đó không thể có giá trị null.

### 2.2. Collection Types
- **List**: Đại diện cho một danh sách các giá trị của cùng một kiểu. Ví dụ: `[Int]` là một danh sách các số nguyên.
- **Non-Null**: Đảm bảo rằng một trường không thể có giá trị null. Ví dụ: `String!` biểu thị rằng trường đó phải luôn có một giá trị chuỗi.

Ví dụ:
```graphql
type Post {
    id: ID!
    title: String!
    tags: [String!]!  # Danh sách các chuỗi không null, và danh sách này cũng không thể null
}
```

### 2.3. Custom Types/Object Types
Ngoài các loại dữ liệu nguyên thủy, GraphQL cho phép bạn định nghĩa các loại dữ liệu tùy chỉnh (custom types) để mô hình hóa các đối tượng phức tạp hơn. Các loại này được gọi là Object Types và có thể bao gồm các trường với các kiểu dữ liệu khác nhau.

Ví dụ:
```graphql
type Author {
    id: ID!
    name: String!
    posts: [Post!]!
}

type Post {
    id: ID!
    title: String!
    content: String!
}
```
> Trong ví dụ trên, `Author` và `Post` là các Object Types với các trường dữ liệu khác nhau. `Author` có một trường `posts` là một danh sách các đối tượng `Post`.

### 2.4. Enum Types
Enum Types cho phép bạn định nghĩa một tập hợp các giá trị hằng số. Điều này hữu ích khi bạn muốn giới hạn giá trị của một trường chỉ trong một số lựa chọn cụ thể
Ví dụ:
```graphql
enum Status {
    DRAFT
    PUBLISHED
    ARCHIVED
}
type Article {
    id: ID!
    title: String!
    status: Status!
}
```

### 2.5. Special Types
Ngoài ra, GraphQL còn hỗ trợ các loại đặc biệt như:
- **Query**: Định nghĩa các truy vấn mà khách hàng có thể thực hiện để lấy dữ liệu. (Giống như GET trong REST)
- **Mutation**: Định nghĩa các thao tác thay đổi dữ liệu (tạo, cập nhật, xóa). (Giống như POST, PUT, PATCH, DELETE trong REST)
- **Subscription**: Định nghĩa các thao tác để theo dõi các sự kiện thời gian thực. (Giống như SSE/WebSocket)

Ví dụ:
```graphql
type Query {
    getUser(id: ID!): User
    getPosts: [Post!]!
}
type Mutation {
    createPost(title: String!, content: String!): Post
}
type Subscription {
    postAdded: Post
}
```

### 2.6. Input Types
Input Types được sử dụng để định nghĩa các đối tượng đầu vào cho các truy vấn và mutation
Ví dụ:
```graphql
input PostInput {
    title: String!
    content: String!
}   
type Mutation {
    createPost(input: PostInput!): Post
}
```

## 3. Tích hợp Spring GraphQL vào dự án Spring Boot
Để tích hợp Spring GraphQL vào dự án Spring Boot, bạn cần thêm các phụ thuộc cần thiết vào tệp `build.gradle.kts` hoặc `pom.xml` của bạn.
### 3.1. Thêm phụ thuộc vào Gradle
```kotlin
dependencies {
    implementation("org.springframework.boot:spring-boot-starter-graphql")
    implementation("com.graphql-java:graphql-java-tools:11.0.0") // Thư viện hỗ trợ định nghĩa schema GraphQL
    implementation("org.springframework.boot:spring-boot-starter-webflux") // Nếu bạn muốn sử dụng WebFlux
}
```
### 3.2. Thêm phụ thuộc vào Maven
```xml
<dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-graphql</artifactId>
    </dependency>
    <!-- Nếu bạn muốn sử dụng WebFlux -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-webflux</artifactId>
    </dependency>
</dependencies>
```

### 3.3. Cấu hình `application.properties` cho Spring GraphQL
Sau khi thêm các phụ thuộc, bạn có thể cấu hình các thuộc tính liên quan đến GraphQL trong tệp `application.properties` hoặc `application.yml`, dưới đây là một số cấu hình cơ bản:
```properties
# Đường dẫn đến các tệp schema GraphQL (mặc định là classpath:graphql - src/main/resources/graphql)
spring.graphql.schema.locations=classpath:graphql/**/

# Đường dẫn endpoint GraphQL (mặc định là /graphql), vì Spring Boot đang sử dụng các endpoint REST khác nên bạn có thể thay đổi nếu cần
spring.graphql.http.path=/graphql

# Kích hoạt giao diện GraphiQL để thử nghiệm các truy vấn GraphQL (mặc định là false)
spring.graphql.graphiql.enabled=true
# Đường dẫn đến giao diện GraphiQL (mặc định là /graphiql)
spring.graphql.graphiql.path=/graphiql
# Cấu hình CORS cho endpoint GraphQL
spring.graphql.cors.allowed-origins=*
spring.graphql.cors.allowed-methods=GET,POST,OPTIONS,PUT,DELETE
```

### 3.4. Định nghĩa Schema GraphQL
Tạo một thư mục `graphql` trong `src/main/resources` và thêm các tệp schema GraphQL với phần mở rộng `.graphqls`. Ví dụ, bạn có thể tạo tệp `schema.graphqls` với nội dung sau:
```graphql
type Query {
    sayHello: String # Truy vấn
    sayHelloTo(name: String!): String # Truy vấn với tham số
}
```
### 3.5. Tạo Controller GraphQL
Tạo một lớp controller để xử lý các truy vấn GraphQL. Ví dụ:
```kotlin
import org.springframework.graphql.data.method.annotation.QueryMapping
import org.springframework.stereotype.Controller
@Controller
class GraphQLController {
    @QueryMapping // Ánh xạ truy vấn GraphQL
    fun sayHello(): String {
        return "Hello, GraphQL with Spring!"   
    }
    
    @QueryMapping("sayHelloTo")
    fun sayHelloTo(@Argument name: String): Mono<String> {
        return Mono.fromSupplier { "Hello, $name!" }
    }
}
```
> Lưu ý: 
> - Sử dụng `@QueryMapping` để ánh xạ các truy vấn GraphQL thay vì `@GetMapping` hoặc các annotation REST khác.
> - Ngoài `@QueryMapping`, bạn cũng có thể sử dụng `@MutationMapping` để ánh xạ các mutation GraphQL.
> - Annotation `@Controller` được sử dụng để đánh dấu lớp này là một controller trong Spring, thay vì sử dụng `@RestController` như trong các ứng dụng REST thông thường.
> - Tên phương thức phải trùng với tên truy vấn trong schema GraphQL. Nếu không muốn trùng tên, bạn có thể set tên trong annotation, ví dụ: `@QueryMapping("sayHello")`.
> - Sử dụng `@Argument` để lấy tham số từ truy vấn GraphQL. Tên tham số trong phương thức phải trùng với tên tham số trong schema GraphQL, nếu không bạn có thể set tên trong annotation, ví dụ: `@Argument("name")`.
> - Với annotation `@SchemaMapping`, bạn có thể ánh xạ các field trong các object type tùy chỉnh. Dùng khi bạn có các object type phức tạp và muốn định nghĩa cách lấy dữ liệu cho các field cụ thể.
```kotlin
@SchemaMapping(
    typeName = "Query", // Tên object type trong schema GraphQL
)
fun authors(): List<Author> {
    // Logic để lấy danh sách tác giả
}

@SchemaMapping(
    typeName = "Author", // Tên object type trong schema GraphQL
    field = "posts" // Tên field trong object type, có type mà không thuộc Scalar Types mà được định nghĩa trong schema bởi bạn
)
fun getPosts(author: Author): List<Post> { // author là field parent được truyền vào
    // Logic để lấy danh sách bài viết của tác giả
}
// Thay vì:
@QueryMapping
fun postsByAuthor(authorId: ID): List<Post> {
    // Logic để lấy danh sách bài viết của tác giả
}
```

```graphql
type Query {
    authors: [Author!]!  # Field authors sẽ được ánh xạ bởi @SchemaMapping
}
type Author {
    id: ID!
    name: String!
    posts: [Post!]!  # Field posts sẽ được ánh xạ bởi @SchemaMapping
}
type Post {
    id: ID!
    title: String!
    content: String!
}
```

### 3.6. Chạy ứng dụng
Chạy ứng dụng Spring Boot của bạn và truy cập vào giao diện GraphiQL tại `http://localhost:8080/graphiql` để thử nghiệm các truy vấn GraphQL. Bạn có thể gửi truy vấn sau để kiểm tra:
```graphql
{
  sayHello
  sayHelloTo(name: "Spring")  # Truy vấn với tham số name
}
```
Kết quả trả về sẽ là:
```json
{
  "data": {
    "sayHello": "Hello, GraphQL with Spring!",
    "sayHelloTo": "Hello, Spring!"
  }
}
```

GraphQL có thể gộp nhiều truy vấn trong một yêu cầu duy nhất, giúp giảm số lần gọi mạng và cải thiện hiệu suất ứng dụng. Trong khi đó nếu sử dụng REST, bạn thường phải thực hiện nhiều yêu cầu HTTP riêng biệt để lấy dữ liệu từ các endpoint khác nhau.
> Ví dụ: Có 3 truy vấn trong một yêu cầu GraphQL, mỗi truy vấn có độ trễ là 200ms, tổng thời gian thực hiện sẽ là 200ms (Giống cơ chế Mono.zip). Trong khi đó, nếu sử dụng REST, bạn sẽ phải thực hiện 3 yêu cầu HTTP riêng biệt, tổng thời gian thực hiện sẽ là 600ms (200ms x 3).

## 4. Một số ví dụ nâng cao
### 4.1. Sử dụng Custom Types với Input Types
Ví dụ này minh hoạ cách:
- Định nghĩa **custom type** (`type Customer`) trong schema GraphQL và ánh xạ sang DTO Kotlin để trả về dữ liệu có cấu trúc (không chỉ là scalar).
- Định nghĩa **input type** (`input AgeRangeFilter`) và bind vào code thông qua `@Argument filter: AgeRangeFilter` để thực hiện lọc/phân trang/tìm kiếm theo object đầu vào.

#### 4.1.1. Các file liên quan
- Schema: `src/main/resources/graphql/custom-type/customers.graphqls`
- DTO: `src/main/kotlin/com/didan/demo/graphql/custom_type/dto/Customer.kt`
- Input DTO: `src/main/kotlin/com/didan/demo/graphql/custom_type/dto/AgeRangeFilter.kt`
- Service: `src/main/kotlin/com/didan/demo/graphql/custom_type/service/CustomerService.kt`
- Controller: `src/main/kotlin/com/didan/demo/graphql/custom_type/controller/CustomerController.kt`

> Lưu ý: project đang cấu hình `spring.graphql.schema.locations=classpath:graphql/custom-type` trong `src/main/resources/application.properties`, nên Spring GraphQL chỉ load schema trong thư mục `graphql/custom-type`.

#### 4.1.2. Định nghĩa schema với Custom Type `Customer`
File `customers.graphqls` định nghĩa:
- `type Customer`: object type gồm các field `id`, `name`, `age`, `city`
- `input AgeRangeFilter`: object đầu vào dùng để filter theo khoảng tuổi
- `type Query`: các query để lấy danh sách, lấy theo id, lọc theo tên, và lọc theo khoảng tuổi

```graphql
type Query {
  customers: [Customer]!
  customerById(id: ID!): Customer
  customersNameContains(name: String!): [Customer]
  customersByAgeRange(filter: AgeRangeFilter!): [Customer]!
}

input AgeRangeFilter {
  minAge: Int!
  maxAge: Int!
}

type Customer {
  id: ID
  name: String
  age: Int
  city: String
}
```

Giải thích nhanh về nullability:
- `customers: [Customer]!` nghĩa là **danh sách không null** (nhưng phần tử bên trong có thể null vì đang là `Customer` thay vì `Customer!`).
- `customerById(...): Customer` có thể trả về `null` khi không tìm thấy.

#### 4.1.3. DTO output/input và cách Spring bind `@Argument`
**Output DTO** Kotlin (tương ứng `type Customer`):
```kotlin
data class Customer(val id: Int, val name: String, val age: Int, val city: String)
```
Khi resolver trả về `Customer`, GraphQL Java sẽ đọc các property `id/name/age/city` để map sang các field tương ứng trong schema. Client chỉ nhận đúng những field mà họ query.

> `ID` trong GraphQL thường serialize như chuỗi. Ở đây code dùng `Int` cho `id`; Spring GraphQL sẽ cố gắng convert input `id` (ví dụ `"1"`) sang `Int` khi bind vào `@Argument id: Int`.

**Input DTO** Kotlin (tương ứng `input AgeRangeFilter`):
```kotlin
data class AgeRangeFilter(val minAge: Int, val maxAge: Int)
```

Khi query nhận argument là một input object, Spring GraphQL sẽ bind trực tiếp sang DTO tương ứng:
```kotlin
@QueryMapping
fun customersByAgeRange(@Argument filter: AgeRangeFilter): Flux<Customer> {
    return customerService.withinAge(filter)
}
```

Lưu ý nhanh:
- Tên field trong `input` (`minAge`, `maxAge`) nên trùng với tên property trong DTO để bind tự động.
- Nếu muốn field optional, đổi schema thành `minAge: Int` (không có `!`) và DTO dùng `Int?`.

#### 4.1.4. Luồng hoạt động (end-to-end)

### 4.2. Sử dụng Nested Object - Schema Design
`Nested Object` (đối tượng lồng nhau) là một kỹ thuật thiết kế schema GraphQL phổ biến để mô hình hóa các quan hệ phức tạp giữa các thực thể. Thay vì trả về tất cả dữ liệu trong một object phẳng, bạn có thể tổ chức dữ liệu thành các object con, giúp schema rõ ràng và dễ hiểu hơn.

Ví dụ trong project này mô tả quan hệ **1-N**: `Customer` có nhiều `CustomerOrder` (đơn hàng). Client có thể query `orders` theo từng customer và truyền argument (ví dụ `limit`) ngay tại field nested.

#### 4.2.1. Các file liên quan
- Schema: `src/main/resources/graphql/nested-object/schema.graphqls`
- Controller (resolver): `src/main/kotlin/com/didan/demo/graphql/nested_object/controller/CustomerController.kt`
- DTO: `src/main/kotlin/com/didan/demo/graphql/nested_object/dto/Customer.kt`
- DTO: `src/main/kotlin/com/didan/demo/graphql/nested_object/dto/CustomerOrderDto.kt`
- Service: `src/main/kotlin/com/didan/demo/graphql/nested_object/service/CustomerService.kt`
- Service: `src/main/kotlin/com/didan/demo/graphql/nested_object/service/OrderService.kt`

> Lưu ý cấu hình schema: hiện `application.properties` đang set `spring.graphql.schema.locations=classpath:graphql/custom-type`. Nếu muốn chạy example nested object, đổi thành `classpath:graphql/nested-object` (hoặc `classpath:graphql/**/` nếu muốn load tất cả schema).

#### 4.2.2. Schema `schema.graphqls` và ý nghĩa “nested object”
Schema định nghĩa:
- Root query `customers` trả về danh sách `Customer`
- `Customer` có field `orders(limit: Int!)` trả về danh sách `CustomerOrder`
- `limit` là argument đặt ngay tại nested field để giới hạn số order trả về (một ví dụ điển hình của schema design trong GraphQL)

```graphql
type Query {
  customers: [Customer]!
}

type Customer {
  id: ID!
  name: String
  age: Int
  city: String
  orders(limit: Int!): [CustomerOrder]!
}

type CustomerOrder {
  id: ID!
  description: String
}
```

Điểm quan trọng:
- `orders` không nằm ở root query, mà “đi theo” từng `Customer`. Client có thể chọn lấy `orders` hoặc không (tuỳ selection set).
- Mỗi nested field có thể có argument riêng (ở đây là `limit`) để server xử lý theo ngữ cảnh “của customer đó”.

#### 4.2.3. Resolver cho root field `Query.customers`
Trong `CustomerController.kt`, method `customers()` được map vào field `customers` của `type Query` bằng `@SchemaMapping(typeName = "Query")`:
```kotlin
@SchemaMapping(typeName = "Query")
fun customers(): Flux<Customer> {
    return customerService.allCustomers()
}
```

`CustomerService.allCustomers()` trả về `Flux<Customer>` (dữ liệu demo in-memory). Sau khi có danh sách customer, GraphQL engine sẽ resolve tiếp các field mà client yêu cầu trong selection set.

> Với Spring GraphQL, root query có thể dùng `@QueryMapping`. Ở đây dùng `@SchemaMapping(typeName = "Query")` là tương đương về ý nghĩa: map method vào field trên type `Query`.

#### 4.2.4. Resolver cho nested field `Customer.orders(limit: Int!)`
`Customer` DTO không có property `orders`, nên để resolve field này, controller khai báo một field resolver riêng:
```kotlin
@SchemaMapping(typeName = "Customer", field = "orders")
fun orders(customer: Customer, @Argument limit: Long): Flux<CustomerOrderDto> {
    return orderService.ordersByCustomerName(customer.name).take(limit)
}
```

Cách Spring GraphQL bind tham số:
- `customer: Customer` là **source/parent object** (customer hiện tại) mà GraphQL đang resolve.
- `@Argument limit` là argument được truyền từ query tại field `orders(limit: ...)`.

Ở đây `limit` trong schema là `Int!` nhưng code nhận `Long`; Spring sẽ convert tự động. Nếu muốn “khớp” tuyệt đối, có thể dùng `Int` trong code.

Ngoài ra, `CustomerOrderDto.id` đang là `UUID`. Khi map sang GraphQL `ID`, Spring GraphQL sẽ serialize ra chuỗi (string) trong response.

### 4.3. Sử dụng `BatchMapping` để giải quyết N+1 problem
Khi sử dụng nested object trong GraphQL, việc gọi resolver cho mỗi object con có thể dẫn đến vấn đề N+1 queries, đặc biệt khi có nhiều object cha. Để giải quyết vấn đề này, Spring GraphQL cung cấp annotation `@BatchMapping`, cho phép bạn xử lý nhiều object con trong một lần gọi duy nhất.

Về bản chất, batching thường được hiện thực bằng **DataLoader** (gom nhiều “key” rồi load một lần). Với Spring GraphQL, bạn không cần tự viết `DataLoaderRegistry` cho case cơ bản này: `@BatchMapping` sẽ giúp đăng ký batch loader theo field và gom các source object trong **cùng một GraphQL request** trước khi gọi service.

Ví dụ trong project này vẫn là quan hệ **1-N**: `Customer` có nhiều `CustomerOrder`, nhưng thay vì resolve `orders` theo từng customer (gây N+1), ta **gom nhiều customer trong cùng request** rồi fetch orders một lần theo batch.

#### 4.3.1. Các file liên quan
- Schema: `src/main/resources/graphql/batch-mapping/schema.graphqls`
- Controller (resolver): `src/main/kotlin/com/didan/demo/graphql/batch_mapping/controller/CustomerController.kt`
- DTO: `src/main/kotlin/com/didan/demo/graphql/batch_mapping/dto/Customer.kt`
- DTO: `src/main/kotlin/com/didan/demo/graphql/batch_mapping/dto/CustomerOrderDto.kt`
- Service: `src/main/kotlin/com/didan/demo/graphql/batch_mapping/service/CustomerService.kt`
- Service: `src/main/kotlin/com/didan/demo/graphql/batch_mapping/service/OrderService.kt`

> Lưu ý cấu hình schema: hiện `application.properties` đang set `spring.graphql.schema.locations=classpath:graphql/custom-type`. Nếu muốn chạy example batch mapping, đổi thành `classpath:graphql/batch-mapping` (hoặc `classpath:graphql/**/`).

#### 4.3.2. Schema `batch-mapping/schema.graphqls`
Khác với ví dụ nested object ở trên, field `orders` ở đây không nhận argument để tập trung vào batching:
```graphql
type Query {
  customers: [Customer]!
}

type Customer {
  id: ID!
  name: String
  age: Int
  city: String
  orders: [CustomerOrder]!
}

type CustomerOrder {
  id: ID!
  description: String
}
```

#### 4.3.3. Vấn đề N+1 xảy ra như thế nào?
Giả sử client query:
```graphql
{
  customers {
    name
    orders {
      description
    }
  }
}
```

Nếu resolve `orders` bằng `@SchemaMapping(typeName="Customer", field="orders")` theo kiểu “1 customer → 1 lần gọi service”, thì:
- 1 lần gọi để lấy danh sách customers (1)
- N lần gọi để lấy orders cho từng customer (N)

Tổng cộng ~ **N + 1** lần gọi (N+1 problem). Với data source thật (DB/HTTP), điều này thường làm chậm đáng kể khi N lớn.

#### 4.3.4. Root resolver: `Query.customers`
Tương tự ví dụ trước, `customers()` được map vào `type Query`:
```kotlin
@SchemaMapping(typeName = "Query")
fun customers(): Flux<Customer> {
    return customerService.allCustomers()
}
```

#### 4.3.5. Batch resolver: `Customer.orders` với `@BatchMapping`
Trong `CustomerController.kt`, field `orders` được resolve bằng `@BatchMapping`:
```kotlin
@BatchMapping(typeName = "Customer", field = "orders")
fun orders(list: List<Customer>): Flux<List<CustomerOrderDto>> {
    return orderService.ordersByCustomerName(
        list.stream().map { it.name }.collect(Collectors.toList())
    )
}
```

Ý nghĩa:
- Thay vì nhận 1 `customer`, method nhận `List<Customer>` (toàn bộ các customer cần resolve `orders` trong cùng request).
- Chỉ **1 lần** gọi `OrderService` cho tất cả tên customer.
- Kết quả trả về phải “khớp” với danh sách input:
  - Có thể trả về `Map<Customer, List<CustomerOrderDto>>` (map theo source)
  - Hoặc như ví dụ này: trả về stream `Flux<List<CustomerOrderDto>>` sao cho **thứ tự kết quả tương ứng thứ tự `list`**.

Trong `OrderService.ordersByCustomerName(names)`, code dùng:
- `flatMapSequential` để giữ đúng thứ tự theo `names` (vì có `delay` mô phỏng độ trễ ngẫu nhiên)
- `defaultIfEmpty(emptyList())` để đảm bảo customer không có order thì vẫn có `[]` (không bị thiếu phần tử)

#### 4.3.6. Luồng hoạt động (BatchMapping vs SchemaMapping)
```mermaid
sequenceDiagram
  autonumber
  actor Client
  participant Spring as Spring GraphQL
  participant Controller as CustomerController
  participant CustomerSvc as CustomerService
  participant OrderSvc as OrderService

  Client->>Spring: POST /graphql (customers { ... orders { ... } })
  Spring->>Controller: Resolve Query.customers()
  Controller->>CustomerSvc: allCustomers()
  CustomerSvc-->>Spring: Flux<Customer>

  Note over Spring: Tập hợp các Customer cần resolve field orders
  Spring->>Controller: Resolve Customer.orders (Batch)\ninput = List<Customer>
  Controller->>OrderSvc: ordersByCustomerName(List<String> names)
  OrderSvc-->>Controller: Flux<List<CustomerOrderDto>> (cùng kích thước, đúng thứ tự)
  Controller-->>Spring: Flux<List<CustomerOrderDto>>

  Spring-->>Client: JSON response
```

So sánh nhanh:
- `@SchemaMapping` (naive): gọi `orders(customer)` N lần
- `@BatchMapping`: gọi `orders(listOfCustomers)` 1 lần cho cả batch (trên cùng field, trong 1 request)

### 4.4. Data Fetching từ nhiều Controller khác nhau
Trong các ứng dụng Spring GraphQL phức tạp, bạn có thể muốn tổ chức các resolver của mình thành nhiều controller khác nhau để tách biệt các chức năng và cải thiện khả năng bảo trì. Spring GraphQL hỗ trợ việc này một cách dễ dàng.

Ví dụ trong project này minh hoạ việc **nhiều controller cùng “đóng góp” resolver cho cùng một GraphQL type** (`Customer`), nhưng mỗi controller phụ trách một phần dữ liệu:
- `CustomerController` trả về danh sách `Customer` (root query)
- `AddressController` resolve field `Customer.address`
- `AccountController` resolve field `Customer.account`

- DTO: `src/main/kotlin/com/didan/demo/graphql/data_fetching_multiple/dto/Customer.kt`

#### 4.4.2. Schema được tách nhiều file và cơ chế “merge” schema
Trong GraphQL, bạn có thể tách schema ra nhiều file để dễ quản lý theo domain. Spring GraphQL sẽ load **tất cả** file `*.graphqls` trong schema location và merge thành một schema thống nhất.

`schema.graphqls` định nghĩa root query và `Customer`:
```graphql
type Query {
  customers: [Customer]!
}

type Customer {
  id: ID!
  name: String
  age: Int
  address: Address
  account: Account
}
```

`address.graphqls` và `account.graphqls` định nghĩa các type liên quan:
```graphql
type Address {
  street: String
  city: String
}
```

```graphql
type Account {
  id: ID
  amount: Int
  accountType: AccountType
}

enum AccountType {
  SAVING
  CHECKING
}
```

#### 4.4.3. Data fetching từ multiple controller hoạt động ra sao?
Điểm quan trọng là: GraphQL “map” dữ liệu theo **field**, không theo “endpoint/controller” như REST.

Trong ví dụ này:
- `CustomerController.customers()` cung cấp danh sách `Customer` (source object)
- Khi client query thêm `address` hoặc `account`, Spring GraphQL sẽ tìm data fetcher tương ứng cho field đó và gọi method trong controller đúng trách nhiệm.

`CustomerController` (root query):
```kotlin
@QueryMapping
fun customers(environment: DataFetchingEnvironment): Flux<Customer> =
    customerService.allCustomers()
```

`AddressController` (nested field resolver):
```kotlin
@SchemaMapping(typeName = "Customer", field = "address")
fun address(customer: Customer): Mono<Address> =
    Mono.just(Address("${customer.name}'s Street", "${customer.name}'s City"))
```

`AccountController` (nested field resolver):
```kotlin
@SchemaMapping(typeName = "Customer", field = "account")
fun account(customer: Customer): Mono<Account> =
    Mono.just(Account(UUID.randomUUID(), ThreadLocalRandom.current().nextInt(1, 1000), "CHECKING"))
```
> `accountType` trong schema là `enum AccountType`, còn DTO đang trả về `String` (`"CHECKING"`/`"SAVING"`). Miễn là string khớp tên enum, GraphQL Java vẫn serialize được.

Lưu ý:
- Tham số `customer: Customer` trong `@SchemaMapping` là **source/parent object** của field đang resolve.
- Các field scalar như `id/name/age` sẽ được GraphQL Java tự đọc từ property của DTO nếu không có resolver override.
- Mỗi field (cặp `typeName` + `field`) nên có đúng 1 resolver. Nếu có 2 controller cùng map vào `Customer.account` thì sẽ gây xung đột/ambiguous mapping khi startup.

#### 4.4.4. `DataFetchingEnvironment` dùng để làm gì?
`CustomerController.customers(environment: DataFetchingEnvironment)` cho thấy bạn có thể lấy thêm context của request:
- Query document, operation name, arguments, selection set
- Auth context (tuỳ cấu hình), locale, extensions...

Case điển hình: logging, authorization theo field, hoặc tối ưu fetch theo selection set (chỉ load những gì client cần).
