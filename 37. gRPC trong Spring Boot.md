# gRPC trong Spring Boot
## 1. Giới thiệu
gRPC (gRPC Remote Procedure Call) là một framework RPC mã nguồn mở được phát triển bởi Google. gRPC sử dụng HTTP/2 làm giao thức truyền tải và Protobuf (Protocol Buffers) làm định dạng dữ liệu. gRPC hỗ trợ nhiều ngôn ngữ lập trình khác nhau và cho phép các dịch vụ giao tiếp với nhau một cách hiệu quả và nhanh chóng.

gRPC được sử dụng rộng rãi trong các ứng dụng microservices, nơi mà các dịch vụ cần giao tiếp với nhau qua mạng. gRPC cung cấp nhiều tính năng mạnh mẽ như xác thực, mã hóa, truyền tải dữ liệu nhị phân và hỗ trợ streaming (truyền tải dữ liệu liên tục).

## 2. So sánh gRPC với REST
|| Tiêu chí | gRPC | REST |
|---|---|---|---|
| 1 | Giao thức | HTTP/2 | HTTP/1.1 |
| 2 | Định dạng dữ liệu | Protobuf | JSON |
| 3 | Tốc độ | Nhanh hơn | Chậm hơn |
| 4 | Streaming | Hỗ trợ | Không hỗ trợ |

Ưu điểm của gRPC:
- Tốc độ nhanh hơn so với REST nhờ sử dụng HTTP/2 và Protobuf.
- Hỗ trợ streaming (truyền tải dữ liệu liên tục) giúp tiết kiệm băng thông và tăng hiệu suất.
- Hỗ trợ nhiều ngôn ngữ lập trình khác nhau.
- Hỗ trợ xác thực và mã hóa dữ liệu.

Nhược điểm của gRPC:
- Cần cài đặt thêm thư viện gRPC trên client và server.
- Không hỗ trợ trình duyệt web (cần sử dụng gRPC-Web để hỗ trợ trình duyệt).
- Cần có kiến thức về Protobuf để định nghĩa các dịch vụ và thông điệp.

Kết hợp giữa gRPC và REST:
- Có thể sử dụng gRPC cho các dịch vụ backend hoặc microservices giao tiếp với nhau, trong khi sử dụng REST cho các dịch vụ frontend hoặc client giao tiếp với server.

VD: User gọi API REST để lấy thông tin tài khoản, sau đó gọi API gRPC để lấy thông tin chi tiết về tài khoản đó ở dưới backend.

## 3. Protocol Buffers (Protobuf)
Protocol Buffers (Protobuf) là một ngôn ngữ định nghĩa giao thức (Interface Definition Language - IDL) và một thư viện để tuần tự hóa dữ liệu (data serialization). Protobuf được phát triển bởi Google và được sử dụng rộng rãi trong các hệ thống phân tán và microservices.

Protobuf cho phép bạn định nghĩa các cấu trúc dữ liệu (messages) và dịch vụ (services) trong một file `.proto`. Sau đó, bạn có thể sử dụng trình biên dịch Protobuf để tạo mã nguồn cho nhiều ngôn ngữ lập trình khác nhau từ file `.proto` này.

### 3.1. So sánh Protobuf với JSON
|| Tiêu chí | Protobuf | JSON |
|---|---|---|---|
| 1 | Kích thước dữ liệu | Nhỏ hơn | Lớn hơn |
| 2 | Tốc độ tuần tự hóa | Nhanh hơn | Chậm hơn |
| 3 | Định dạng | Nhị phân | Văn bản |
| 4 | Khả năng mở rộng | Dễ dàng mở rộng | Khó mở rộng |

### 3.2. Cú pháp cơ bản của Protobuf
- Định nghĩa message:
```proto
syntax = "proto3"; // Khai báo sử dụng phiên bản proto3

option java_package = "com.example"; // Chỉ định package cho mã Java được sinh ra sau khi biên dịch .proto

// option go_package = "example"; // Chỉ định package cho mã Go được sinh ra sau khi biên dịch .proto
// option csharp_namespace = "Example"; // Chỉ định namespace cho mã C# được sinh ra sau khi biên dịch .proto

package example; // Đặt tên package cho file proto (Tránh trường hợp xung đột tên khi có nhiều file cùng tên .proto, cùng tên message, ...) Nên để file proto trong các thư mục con khác nhau tương ứng với tên package

java_multiple_files = true; // Tạo nhiều file Java từ một file proto (mỗi message và service sẽ được tạo thành một file Java riêng biệt)

// message định nghĩa một cấu trúc dữ liệu
// Định nghĩa theo cú pháp
/*
message <TênMessage> {
  <KiểuDữLiệu> <TênTrường> = <SốThứTự>;
  ...
}
*/
message Book {
  int32 book_id = 1; // ID của sách (số thứ tự 1)
  string title = 2;  // Tiêu đề sách (số thứ tự 2)
  float price = 3;   // Giá sách (số thứ tự 3)
  int32 pages = 4;   // Số trang (số thứ tự 4)
  int32 author_id = 5; // ID tác giả (số thứ tự 5)
}

enum Type {
  UNKNOWN = 0;
  FICTION = 1;
  SCIENCE = 2;
  BIOGRAPHY = 3;
}

message Author {
  int32 author_id = 1;  // ID tác giả
  string first_name = 2; // Tên tác giả
  string last_name = 3;  // Họ tác giả
  string gender = 4;     // Giới tính
  repeated Book books = 5;     // Danh sách sách sách của tác giả
  map<string, string> contacts = 6; // Thông tin liên lạc (key: loại liên lạc, value: thông tin)
  Type author_type = 7;  // Loại tác giả
  reserved 8, 9; // Đánh dấu số thứ tự 8, 9 đã bị loại bỏ, tránh tái sử dụng trong tương lai
  reserved "middle_name", "age"; // Đánh dấu tên trường middle_name, age đã bị loại bỏ, tránh tái sử dụng trong tương lai
}

// oneof: Chỉ một trong các trường được set
message Phone {
  int32 number = 1;
  int32 code = 2;
}

message Email {
  string address = 1;
  string password = 2;
}

messgage ContactInfo {
  oneof contact_method { // Trường này có thể có kiểu dữ liệu là Phone hoặc Email, nếu không set thì mặc định là UNKNOWN_CONTACT_METHOD
    Phone phone = 1;
    Email email = 2;
  }
}

```

Sau đó, để compile file `.proto` thành mã nguồn Java, bạn cần sử dụng plugin `protobuf-maven-plugin` trong Maven hoặc `protobuf-gradle-plugin` trong Gradle. Sau khi thêm plugin và cấu hình, bạn có thể chạy lệnh build để tự động sinh mã nguồn từ file `.proto`: `mvn clean compile` hoặc `./gradlew build`.

> Lưu ý số thứ tự các trường:
> - Mỗi trường trong một message phải có số thứ tự duy nhất (số nguyên dương).
> - 1-15: Dành cho các trường thường sử dụng (sử dụng 1 byte khi serialize).
> - 16-2047: Dành cho các trường ít sử dụng hơn (sử dụng 2 byte khi serialize).
> - Số thứ tự 1 là nhỏ nhất, không được sử dụng số thứ tự 0 (vì nó dành cho mục đích nội bộ của Protobuf), số thứ tự lớn nhất là 2^29 - 1 (536,870,911).
> - Số thứ tự không được thay đổi sau khi đã sử dụng, nếu muốn loại bỏ một trường, hãy sử dụng từ khóa `reserved` để đánh dấu số thứ tự hoặc tên trường đã bị loại bỏ, tránh tái sử dụng trong tương lai. (19000 - 19999 được dành riêng cho các mục đích nội bộ của Protobuf).
> - Không được thay đooir số thứ tự của các trường khi nó đã được sử dụng, vì sẽ gây ra lỗi khi deserialize dữ liệu đã được serialize trước đó.
> - Không được thay đổi kiểu dữ liệu của các trường đã được sử dụng, vì sẽ gây ra lỗi khi deserialize dữ liệu đã được serialize trước đó.
> - Hãy sử dụng `reserved` để đánh dấu các trường muốn xóa (loại bỏ) thay vì xóa trực tiếp và gán lại số thứ tự trường khác để tránh tái sử dụng số thứ tự hoặc tên trường đó trong tương lai. Ví dụ:
```proto
// Kiểu Employee ban đầu:

message Employee {
	string first_name = 1;
	int32 age = 2;
	int32 salary = 3;
}

// Sau đó có yêu cầu xóa salary, ta sẽ sử dụng reserved như sau:
message Employee {
  string first_name = 1;
  int32 age = 2;
  reserved 3; // Đánh dấu số thứ tự 3 đã bị loại bỏ
  reserved "salary"; // Đánh dấu tên trường salary đã bị loại bỏ
}

service EmployeeService { // Định nghĩa service EmployeeService

  rpc getEmployee(Employee) returns (Employee); // Phương thức getEmployee nhận vào một Employee và trả về một Employee (client gửi request, server trả về response)

  rpc listEmployees(google.protobuf.Empty) returns (stream Employee); // Phương thức listEmployees không nhận tham số và trả về một luồng (stream) các Employee (server streaming)

  rpc uploadEmployees(stream Employee) returns (google.protobuf.Empty); // Phương thức uploadEmployees nhận vào một luồng (stream) các Employee và trả về một Empty (client streaming)

  rpc chatEmployees(stream Employee) returns (stream Employee); // Phương thức chatEmployees nhận vào và trả về một luồng (stream) các Employee (bidirectional streaming)


}
```

### 3.3. Tính chẩt của file JAVA được sinh ra từ Protobuf
- Các class Java được sinh ra từ Protobuf thường là các class immutable (không thể thay đổi sau khi tạo Chỉ có thể tạo mới hoặc sử dụng Builder để tạo đối tượng mới từ đối tượng cũ, có getter nhưng không có setter).
- Sử dụng Builder pattern để tạo và cấu hình các đối tượng message, muốn sửa đổi giá trị của một trường, bạn cần tạo một đối tượng mới thông qua `toBuilder()` của đối tượng hiện tại.
```java
Book book = Book.newBuilder()
    .setBookId(1)
    .setTitle("Example Book")
    .build();
Book updatedBook = book.toBuilder()
    .setTitle("Updated Title")
    .build();

Book removedFieldBook = book.toBuilder()
    .clearTitle() // Xóa trường title, chứ không được set null
    .build();

Phone phone = Phone.newBuilder()
    .setNumber(123456789)
    .setCode(1)
    .build();

Email email = Email.newBuilder()
    .setAddress("example@example.com")
    .setPassword("password")
    .build();
ContactInfo contactByPhone = ContactInfo.newBuilder()
    .setPhone(phone) // Chỉ set phone
    .build();
ContactInfo contactByEmail = ContactInfo.newBuilder()
    .setEmail(email) // Chỉ set email
    .build();
```

- Objects được tạo ra không thể set null cho các trường, nếu không set giá trị cho một trường, nó sẽ có giá trị mặc định (0 cho số, rỗng cho chuỗi, false cho boolean). 
- Sử dụng các phương thức `has<FieldName>()` để kiểm tra xem một trường có được set hay không (chỉ áp dụng cho các trường message và enum).

| Protobuf Type | Java Type | Default Value | Mô tả |

| double | double | 0.0 | Số thực 64-bit |

| uint32 | int | 0 | Số nguyên không dấu 32-bit |
| int64 | long | 0L | Số nguyên 64-bit |
| sint64 | long | 0L | Số nguyên 64-bit (sử dụng mã hóa zigzag) |
| uint64 | long | 0L | Số nguyên không dấu 64-bit |
| bool | boolean | false | Giá trị boolean |
| string | String | "" | Chuỗi UTF-8 |

| reserved + <field numbers/names> | N/A | N/A | Dùng để đánh dấu các số thứ tự hoặc tên trường đã bị loại bỏ, tránh tái sử dụng trong tương lai |

### 3.5. Serialization và Deserialization
- Protobuf sử dụng định dạng nhị phân để tuần tự hóa (serialization) và giải tuần tự hóa (deserialization) dữ liệu, giúp tiết kiệm băng thông và tăng tốc độ truyền tải so với định dạng văn bản như JSON hoặc XML.
- Sử dụng `writeTo(OutputStream output)` để tuần tự hóa một message thành luồng byte, và `parseFrom(InputStream input)` để giải tuần tự hóa từ luồng byte thành một message.

```java
// Giả sử compile file .proto để tạo class Book
Book book = Book.newBuilder()
    .setBookId(1)
    .setTitle("Example Book")
    .setPrice(19.99f)
    .setPages(300)
    .setAuthorId(10)
    .build();
// Serialization
try (var stream = Files.newOutputStream(Path.of("book.bin"))) {
    book.writeTo(stream);
} catch (IOException e) {
    e.printStackTrace();
}
// Deserialization
try (var stream = Files.newInputStream(Path.of("book.bin"))) {
    Book deserializedBook = Book.parseFrom(stream);
    System.out.println("Deserialized Book: " + deserializedBook);
} catch (IOException e) {
    e.printStackTrace();
}

System.out.println("Compare books: " + book.equals(deserializedBook)); // true
```
### 3.6. Import trong Protobuf
- Protobuf hỗ trợ import các file `.proto` khác để tái sử dụng định nghĩa message và service. Trong file `.proto`, bạn có thể sử dụng cú pháp sau để import một file khác:

```proto
import "other.proto"; // Import file other.proto nếu cùng package
import "proto/common/book.proto"; // Import file book.proto nếu khác package (file book.proto nằm trong thư mục proto/common/ đã được định nghĩa package là proto.common)

// Sử dụng message hoặc service từ file đã import
message Library {
  repeated proto.common.Book books = 1; // Sử dụng cú pháp <package>.<MessageName>
}
```
- Ngoài ra, Google cũng cung cấp một số file `.proto` chuẩn trong thư viện `google/protobuf` sau khi compile, bạn có thể import chúng như sau:

```proto
import "google/protobuf/timestamp.proto"; // Import message Timestamp
import "google/protobuf/any.proto"; // Import message Any
import "google/protobuf/wrappers.proto"; // Import các message wrapper như Int32Value, StringValue, ...
import "google/protobuf/empty.proto"; // Import message Empty
```

### 3.7. Proto CI/CD
- Trong quy trình CI/CD, bạn có thể tự động biên dịch các file `.proto` thành mã nguồn Java (hoặc ngôn ngữ khác) mỗi khi có thay đổi trong file `.proto`. Điều này đảm bảo rằng mã nguồn luôn được cập nhật với định nghĩa mới nhất.
- Trong thư mục `protoc-plugins` (sau khi compile), bạn có thể lưu trữ các file `.proto` và sử dụng file `protoc-{version}-{os}.exe` để biên dịch các file `.proto` thành mã nguồn Java trong quá trình build của CI/CD. Cú pháp sử dụng như sau:

```bash
./protoc-<version>-<os>.exe --java_out=./output/path --proto_path=./proto/path ./proto/path/schema.proto
```
Trong đó:
- `--java_out`: Chỉ định thư mục đầu ra để lưu trữ mã nguồn Java được sinh ra. (python_out, cpp_out, go_out, csharp_out, ruby_out, ... tùy theo ngôn ngữ bạn muốn sinh mã nguồn)
- `--proto_path`: Chỉ định thư mục chứa các file `.proto`.
- `./proto/path/schema.proto`: Đường dẫn đến file `.proto` cần biên dịch.

## 4. Mô hình giao tiếp gRPC
gRPC hỗ trợ bốn mô hình giao tiếp chính giữa client và server:
1. **Unary RPC**: Client gửi một request và nhận về một response từ server. Đây là mô hình đơn giản nhất và phổ biến nhất.
   - Ví dụ: Client gửi yêu cầu lấy thông tin người dùng, server trả về thông tin người dùng.
2. **Server Streaming RPC**: Client gửi một request và nhận về một luồng (stream) các response từ server. Server có thể gửi nhiều response cho một request.
    - Ví dụ: Client gửi yêu cầu lấy thông tin giao hàng, server trả về nhiều bản ghi giao hàng theo thời gian thực.
3. **Client Streaming RPC**: Client gửi một luồng (stream) các request đến server và nhận về một response từ server. Client có thể gửi nhiều request trước khi nhận response.
    - Ví dụ: Client gửi nhiều bản ghi cảm biến đến server, server trả về tổng hợp dữ liệu sau khi nhận tất cả các bản ghi.
4. **Bidirectional Streaming RPC**: Client và server cùng gửi và nhận các luồng (stream) các message. Cả hai bên có thể gửi và nhận message độc lập với nhau.
   - Ví dụ: Chat ứng dụng, client và server có thể gửi và nhận tin nhắn liên tục.

## 4.1. Stream Observer trong gRPC
gRPC sử dụng `StreamObserver` để xử lý các luồng (stream) trong các mô hình giao tiếp streaming (Server Streaming, Client Streaming, Bidirectional Streaming).

`StreamObserver<T>` là một interface trong gRPC đại diện cho một luồng các message kiểu T. Nó có ba phương thức chính:
- 1. `onNext(T value)`: Phương thức này được gọi để gửi một message mới trong luồng. Trong server streaming, server sẽ gọi phương thức này để gửi từng response cho client. Trong client streaming, client sẽ gọi phương thức này để gửi từng request đến server.
- 2. `onError(Throwable t)`: Phương thức này được gọi khi có lỗi xảy ra trong luồng. Nó sẽ kết thúc luồng và thông báo lỗi cho bên nhận.
- 3. `onCompleted()`: Phương thức này được gọi để kết thúc luồng một cách bình thường. Nó thông báo rằng không còn message nào sẽ được gửi nữa.

Thông thường `method` của các service trong file `.proto` sẽ có kiểu trả về là `void` (nhìn có vẻ lạ vì không trả về gì cả) nhưng thực chất nó trả về một `StreamObserver<T>` để xử lý các luồng message (`StreanObserver` lại là tham số của phương thức `method` trong abstract class được sinh ra từ file `.proto`). Đây là mô hình kiểu mới, giúp gRPC có thể hỗ trợ tốt các mô hình giao tiếp streaming.

> Request và Response truyền thồng
```java
public T getSomething(Input) {
  ...
  return t;
}
```
> Request và Response với gRPC sử dụng StreamObserver
```java
public void getSomething(Input request, StreamObserver<T> responseObserver) {
  ...
  responseObserver.onNext(t); // Gửi response
  responseObserver.onCompleted(); // Kết thúc luồng
}
```

## 4.2. Cấu hình gRPC Server
Để cấu hình gRPC server trong Spring Boot, có 2 cách phổ biến:
### 4.2.1. Sử dụng thư viện `net.devh:grpc-server-spring-boot-starter` để tích hợp gRPC vào Spring Boot một cách dễ dàng. 
B1: Thêm dependency vào file `pom.xml` của module server:

### 4.2.2. Tự cấu hình gRPC server bằng cách tạo một bean `Server` trong Spring Boot.
```java
import io.grpc.BindableService;
import io.grpc.Server;
import io.grpc.ServerBuilder;
import io.grpc.health.v1.HealthCheckResponse.ServingStatus;
import io.grpc.protobuf.services.HealthStatusManager;
import java.io.IOException;
import java.util.List;
import java.util.concurrent.Executor;
import java.util.concurrent.TimeUnit;
import javax.annotation.PreDestroy;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.boot.context.properties.EnableConfigurationProperties;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Slf4j
@Configuration
@RequiredArgsConstructor
@EnableConfigurationProperties(GrpcProperties.class)
public class GrpcServerConfiguration {

  private Server server; // Đây là instance của gRPC Server
  private Server healthServer; // Đây là instance của gRPC Health Server
  private final ServerTracingInterceptor serverTracingInterceptor; // Đây là interceptor để theo dõi và ghi log các request gRPC, nếu có
  private final GrpcProperties grpcProperties; // Cấu hình gRPC từ file application.yml
  private final HealthStatusManager healthStatusManager = new HealthStatusManager(); // Quản lý trạng thái sức khỏe của gRPC server

  @Bean
  public HealthStatusManager healthStatusManager() {
    return healthStatusManager; // Trả về instance của HealthStatusManager
  }

  @Bean
  public Server grpcServer(
    GrpcProperties grpcProperties, // Inject cấu hình gRPC
    List<BindableService> grpcServices,  // Inject tất cả các dịch vụ gRPC đã được định nghĩa (các class kế thừa BindableService, là các service được sinh ra từ file .proto)
    @Qualifier("ioExecutor") Executor executor // Inject Executor để xử lý các request gRPC bằng thread pool
  ) {
    try {
        server = createServer(grpcProperties, grpcServices, executor);
        var service - server.getServices()
        .stream() // Lấy tất cả các dịch vụ đã đăng ký trên gRPC server
        .mao(ServerServiceDefinition::getServiceDescriptor) // Lấy ServiceDescriptor từ mỗi dịch vụ
        .map(ServiceDescriptor::getName) // Lấy tên dịch vụ từ ServiceDescriptor
        .toList();  // Chuyển đổi sang danh sách
      }
      server.start();
    catch (IOException e) {
      log.error("Failed to start gRPC server", e);
    }
    log.info("gRPC server started successfully on port {}, services: {}", grpcProperties.getConfig().getPort(), service);
    healthStatusManager.setStatus("", ServingStatus.SERVING); // Đặt trạng thái sức khỏe của gRPC server là SERVING (đang hoạt động)
    Runtime.getRuntime().addShutdownHook(new Thread(this::shutDownServer)); // Thêm hook để tắt gRPC server khi JVM shutdown
    return server; // Trả về instance của gRPC Server
  }

  @PreDestroy // Đánh dấu phương thức này sẽ được gọi khi bean bị hủy (khi ứng dụng Spring Boot tắt)
  public void stopServer() {
    shutDownServer(); // Gọi phương thức để tắt gRPC server
  }

  private void shutDownServer() { // Phương thức để tắt gRPC server
    healthStatusManager.setStatus("", ServingStatus.NOT_SERVING); // Đặt trạng thái sức khỏe của gRPC server là NOT_SERVING (không hoạt động)
    if (server != null && !server.isShutdown()) { // Kiểm tra nếu server không null và chưa bị tắt
      log.info("Shutting down gRPC server since JVM is shutting down"); // Ghi log thông báo tắt gRPC server do JVM đang tắt
      try {
        server.shutdown(); // Yêu cầu gRPC server tắt một cách nhẹ nhàng
        if (!server.awaitTermination(grpcProperties.getConfig().getAwaitTermination(), TimeUnit.MILLISECONDS)) { // Chờ server tắt trong khoảng thời gian cấu hình, nếu không thì ép tắt
          log.warn("gRPC server did not shut down in the allocated time. Forcing shutdown.");
          server.shutdownNow(); // Ép tắt gRPC server ngay lập tức
        }
        log.info("gRPC server shut down successfully"); // Ghi log thông báo gRPC server đã tắt thành công
      } catch (InterruptedException e) {
        log.error("gRPC server shut down interrupted", e);
        Thread.currentThread().interrupt(); // Khôi phục trạng thái interrupt của thread
      }
    }
  }

  private Server createServer(GrpcProperties grpcProperties, List<BindableService> grpcServices, Executor executor) {
    ServerBuilder<?> serverBuilder = ServerBuilder // Tạo builder để cấu hình gRPC server
        .forPort(grpcProperties.getConfig().getPort()) // Cấu hình port cho gRPC server
        .addService(healthStatusManager.getHealthService()) // Thêm dịch vụ health check vào gRPC server
        .keepAliveTime(grpcProperties.getConfig().getKeepAliveTime(), TimeUnit.MILLISECONDS) // Cấu hình thời gian keep-alive
        .keepAliveTimeout(grpcProperties.getConfig().getKeepAliveTimeout(), TimeUnit.MILLISECONDS) // Cấu hình timeout cho keep-alive
        .permitKeepAliveWithoutCalls(grpcProperties.getConfig().isKeepAliveWithoutCalls()) // Cấu hình cho phép keep-alive khi không có cuộc gọi
        .permitKeepAliveTime(grpcProperties.getConfig().getPermitKeepAliveTime(), TimeUnit.MILLISECONDS) // Cấu hình thời gian cho phép keep-alive
        .handshakeTimeout(grpcProperties.getConfig().getHandshakeTimeout(), TimeUnit.MILLISECONDS) // Cấu hình timeout cho handshake
        .maxInboundMessageSize(grpcProperties.getConfig().getMaxInboundMessageSize()) // Cấu hình kích thước tối đa của message nhận vào
        .maxInboundMetadataSize(grpcProperties.getConfig().getMaxInboundMetadataSize()) // Cấu hình kích thước tối đa của metadata nhận vào
        .executor(executor) // Cấu hình executor để xử lý các request
        .intercept(serverTracingInterceptor); // Thêm interceptor để theo dõi tracing cho server

    grpcServices.forEach(serverBuilder::addService); // Thêm tất cả các dịch vụ gRPC vào server
    return serverBuilder.build(); // Xây dựng và trả về instance của gRPC Server
  }
}
```

### 4.3.3. Stub - Synchronous (BlockingStub) và Asynchronous (FutureStub, Stub)
Client có thể gọi đến Server thông qua loại Synchronous (BlockingStub) hoặc Asynchronous (FutureStub, Stub):
- **BlockingStub**: Đây là loại stub đồng bộ, nghĩa là khi client gọi một phương thức trên stub này, nó sẽ chặn (block) cho đến khi nhận được phản hồi từ server. Loại stub này phù hợp cho các cuộc gọi unary (một request - một response) và server streaming (một request - nhiều response).
- **FutureStub**: Đây là loại stub bất đồng bộ, nghĩa là khi client gọi một phương thức trên stub này, nó sẽ trả về một đối tượng `ListenableFuture` ngay lập tức mà không chặn. Client có thể sử dụng đối tượng này để đăng ký callback hoặc chờ đợi kết quả sau này. Loại stub này phù hợp cho các cuộc gọi unary và server streaming.
- **Stub**: Đây là loại stub bất đồng bộ, tương tự như FutureStub, nhưng thay vì trả về `ListenableFuture`, nó sử dụng `StreamObserver` để xử lý các phản hồi từ server. Loại stub này phù hợp cho tất cả các mô hình giao tiếp gRPC, bao gồm unary, server streaming, client streaming và bidirectional streaming.

> Đối với Java 21, chúng ta có thể sử dụng `Virtual Thread` để gọi các phương thức bất đồng bộ một cách đồng bộ mà không bị chặn (block). Điều này giúp đơn giản hóa mã nguồn và cải thiện hiệu suất của ứng dụng.

```java
            public void onError(Throwable t) {
                // Xử lý lỗi nếu có
              latch.countDown(); // Giảm đếm latch khi có lỗi xảy ra
            }

            @Override
            public void onCompleted() {
                // Xử lý khi luồng hoàn thành
              latch.countDown(); // Giảm đếm latch khi luồng hoàn thành
            }
        };

        // Gọi service bất đồng bộ và xử lý phản hồi qua StreamObserver
        bookAuthorServiceStubAsync
        .withDeadlineAfter(5, TimeUnit.SECONDS) // Thiết lập thời gian chờ tối đa cho cuộc gọi là 5 giây
        .getAuthor(request, responseObserver); // Gửi request và xử lý response thông qua StreamObserver (method đã được định nghĩa trong service của file .proto)
        try {
            latch.await(6, TimeUnit.SECONDS); // Chờ đợi tối đa 6 giây để cuộc gọi async hoàn thành
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt(); // Khôi phục trạng thái interrupt của thread
        }
    }
}
```

## 4.5. gRPC Server Streaming Service
`Server Streaming` là mô hình giao tiếp trong gRPC mà client gửi một request và nhận về một luồng (stream) các response từ server. Server có thể gửi nhiều response cho một request. Nó được sử dụng phổ biến ở các case như: Cập nhật thời tiết, cập nhật vị trí giao hàng, gía cổ phiếu theo thời gian thực, tải file lớn theo từng phần, ...

`Server Streaming`có thể trả về:
- Một luồng vô hạn (infinite stream): Server liên tục gửi các response mà không bao giờ kết thúc. Client phải xử lý các response liên tục và có thể dừng nhận khi cần thiết.
- Một luồng hữu hạn (finite stream): Server gửi một số lượng response xác định và kết thúc luồng sau khi gửi xong. Client nhận tất cả các response và xử lý chúng.
- Một luồng trống (empty stream): Server không gửi bất kỳ response nào và kết thúc luồng ngay lập tức. Client nhận biết rằng không có dữ liệu để xử lý.
- Một luồng lỗi (error stream): Server gặp lỗi trong quá trình xử lý và gửi lỗi cho client thay vì các response thông thường. Client phải xử lý lỗi này một cách thích hợp.

### 4.5.1. Định nghĩa Service server streaming trong file .proto
```proto
message WithdrawRequest {
    int32 account_number = 1;
    double amount = 2;
}

message Money {
    int32 amount = 1;
}

service BankService {
    rpc Withdraw(WithdrawRequest) returns (stream Money); // Định nghĩa phương thức Withdraw với kiểu trả về là stream Money
}
```

### 4.5.2. Cài đặt Service ở phía Server
Lớp `BankService` kế thừa từ `BankServiceGrpc.BankServiceImplBase` và override phương thức `Withdraw`. Trong phương thức này, chúng ta sẽ kiểm tra số dư tài khoản và gửi các response `Money` về client theo từng phần cho đến khi hết số tiền yêu cầu hoặc hết số dư tài khoản.
```java
@Service
public class BankService extends BankServiceGrpc.BankServiceImplBase {
    private final Map<Integer, Double> accountBalances = new HashMap<>(); // Giả sử có một bản đồ lưu trữ số dư tài khoản

    @Override
    public void withdraw(WithdrawRequest request, StreamObserver<Money> responseObserver) {
        int accountNumber = request.getAccountNumber();
        int amount = request.getAmount();
        int balance = accountBalances.getOrDefault(accountNumber, 0.0);

        if (balance < amount) {
            responseObserver.onError(new RuntimeException("Insufficient funds")); // Gửi lỗi nếu số dư không đủ
            return;
        }

        int remainingAmount = amount;
        while (remainingAmount > 0) {
            int chunk = Math.min(100, remainingAmount); // Gửi từng phần 100 đơn vị tiền tệ
            Money money = Money.newBuilder().setAmount(chunk).build();
            responseObserver.onNext(money); // Gửi response về client
            remainingAmount -= chunk;
            balance -= chunk;
            Uninterruptibles.sleepUninterruptibly(1, TimeUnit.SECONDS); // Giả lập độ trễ giữa các response
        }

        accountBalances.put(accountNumber, balance); // Cập nhật số dư tài khoản
        responseObserver.onCompleted(); // Kết thúc luồng
    }
}
``` 

### 4.5.3. Gọi Service ở phía Client
```java
@Service
@RequiredArgsConstructor
public class BankClientService {

    // Phần cấu hình kết nối gRPC và tạo stub tương tự như phần 4.3.2
    private final BankServiceGrpc.BankServiceStub bankServiceStub; // Inject stub (asynchronous) cho dịch vụ BankService
    private final BankServiceGrpc.BankServiceBlockingStub bankServiceBlockingStub; // Inject stub blocking (synchronous) cho dịch vụ BankService

    /**
     * Gọi phương thức withdraw từ server gRPC
     * @param accountNumber Số tài khoản
     * @param amount Số tiền rút
     */
    public void withdraw(int accountNumber, double amount) {
        WithdrawRequest request = WithdrawRequest.newBuilder()
                .setAccountNumber(accountNumber)
                .setAmount(amount)
                .build();

        StreamObserver<Money> responseObserver = new StreamObserver<Money>() {
            @Override
            public void onNext(Money value) {
                // Xử lý mỗi phần tiền nhận được từ server
                System.out.println("Received money: " + value.getAmount());
            }

            @Override
            public void onError(Throwable t) {
                // Xử lý lỗi nếu có
                System.err.println("Error during withdrawal: " + t.getMessage());
            }

            @Override
            public void onCompleted() {
                // Xử lý khi luồng hoàn thành
                System.out.println("Withdrawal completed.");
            }
        };

        bankServiceStub.withdraw(request, responseObserver); // Gọi service bất đồng bộ và xử lý phản hồi qua StreamObserver
    }

    public void withdrawBlocking(int accountNumber, double amount) {
        WithdrawRequest request = WithdrawRequest.newBuilder()
                .setAccountNumber(accountNumber)
                .setAmount(amount)
                .build();

        Iterator<Money> moneyIterator = bankServiceBlockingStub.withdraw(request); // Gọi service đồng bộ và nhận về iterator các response

        while (moneyIterator.hasNext()) { // Lặp qua từng response từ server
            Money money = moneyIterator.next(); // Lấy từng phần tiền từ iterator
            // Xử lý mỗi phần tiền nhận được từ server
            System.out.println("Received money: " + money.getAmount());
        }

        System.out.println("Withdrawal completed.");
    }
}
```

### 4.5.4. Lưu ý khi sử dụng Server Streaming
Các message response được gửi từ server về client theo thứ tự chúng được tạo ra trên server.

Nên sử dụng `Unary` hay `Streaming` tùy thuộc vào yêu cầu của ứng dụng và tính chất của dữ liệu cần truyền tải:
- Sử dụng `Unary` khi client chỉ cần nhận một response duy nhất cho mỗi request, ví dụ như truy vấn thông tin người dùng, lấy chi tiết sản phẩm, kích thước truyền tải không lớn và không tốn thời gian chờ đợi lâu.
- Sử dụng `Server Streaming` khi client cần nhận nhiều response cho một request, ví dụ như cập nhật thời tiết theo thời gian thực, tải file lớn theo từng phần, kích thước truyền tải lớn hoặc tốn thời gian chờ đợi lâu.

## 4.6. gRPC Client Streaming Service
`Client Streaming` là mô hình giao tiếp trong gRPC mà client gửi một luồng (stream) các request đến server và nhận về một response duy nhất từ server. Client có thể gửi nhiều request cho một cuộc gọi. Nó được sử dụng phổ biến ở các case như: Tải lên file lớn theo từng phần, gửi dữ liệu cảm biến theo thời gian thực, gửi log hoặc sự kiện theo lô, ...

### 4.6.1. Định nghĩa Service client streaming trong file .proto
```proto
message DepositRequest {
  oneof request {
    int32 account_number = 1;
    Money money = 2;
  }
}

message Money {
    int32 amount = 1;
}

message AccountBalance {
    int32 balance = 1;
}

service BankService {
    rpc Deposit(stream DepositRequest) returns (AccountBalance); // Định nghĩa phương thức Deposit với kiểu request là stream DepositRequest và trả về AccountBalance
}
```

### 4.6.2. Cài đặt Service ở phía Server
Class `BankService` kế thừa từ `BankServiceGrpc.BankServiceImplBase` và override phương thức `Deposit`. Trong phương thức này, chúng ta sẽ nhận các request từ client, tính tổng số tiền gửi và trả về số dư tài khoản sau khi gửi xong.
```java
@Service
public class BankService extends BankServiceGrpc.BankServiceImplBase {
    private final Map<Integer, Double> accountBalances = new HashMap<>(); // Giả sử có một bản đồ lưu trữ số dư tài khoản

    /**
     * Ghi đè phương thức deposit để xử lý client streaming
     * @return StreamObserver<DepositRequest> - Trả về một StreamObserver để nhận các request từ client
     */
    @Override
    public StreamObserver<DepositRequest> deposit(StreamObserver<AccountBalance> responseObserver) {
      // Trả về một StreamObserver để nhận các request từ client (StreamObserver bao gồm các phương thức onNext, onError, onCompleted)
        return new StreamObserver<DepositRequest>() {
            private int accountNumber;
            private double totalAmount = 0.0;

            // Xử lý mỗi request nhận được mỗi lần từ client
            @Override
            public void onNext(DepositRequest request) { 
                if (request.hasAccountNumber()) { // Nếu request chứa account_number
                    accountNumber = request.getAccountNumber(); // Lưu số tài khoản
                } else if (request.hasMoney()) { // Nếu request chứa money
                    totalAmount += request.getMoney().getAmount(); // Cộng dồn số tiền gửi
                }
            }

            // Xử lý lỗi nếu có
            @Override
            public void onError(Throwable t) {
                // Xử lý lỗi nếu có
                System.err.println("Error during deposit: " + t.getMessage());
            }

            // Xử lý khi luồng hoàn thành
            @Override
            public void onCompleted() {
                double currentBalance = accountBalances.getOrDefault(accountNumber, 0.0); // Lấy số dư hiện tại của tài khoản
                currentBalance += totalAmount; // Cập nhật số dư sau khi gửi tiền
                accountBalances.put(accountNumber, currentBalance); // Lưu số dư tài khoản vào bản đồ
 
                AccountBalance accountBalance = AccountBalance.newBuilder()
                        .setBalance((int) currentBalance)
                        .build();
                responseObserver.onNext(accountBalance); // Gửi phản hồi về client
                responseObserver.onCompleted(); // Kết thúc luồng
            }
        };
    }
}
```
Hàm `deposit` trả về một `StreamObserver<DepositRequest>` để cho client thực hiện gửi nhiều request. Trong `onNext`, chúng ta xử lý từng request nhận được từ client. Khi client gọi `onCompleted`, chúng ta tính toán số dư tài khoản và gửi phản hồi về client.

### 4.6.3. Gọi Service ở phía Client
Ở phía client, chúng ta sẽ tạo một `StreamObserver<DepositRequest>` để gửi các request đến server và nhận về một response duy nhất.
```java
@Service
@RequiredArgsConstructor
public class BankClientService {

    // Phần cấu hình kết nối gRPC và tạo stub tương tự như phần 4.3.2

    /**
     * Gọi phương thức deposit từ server gRPC
     * @param accountNumber Số tài khoản
     * @param amounts Danh sách số tiền gửi
     */
    public void deposit(int accountNumber, List<Double> amounts) {
      // Tạo StreamObserver để nhận phản hồi từ server (truyền vào phương thức deposit)
        StreamObserver<AccountBalance> responseObserver = new StreamObserver<AccountBalance>() {
            @Override
            public void onNext(AccountBalance value) {
                // Xử lý phản hồi nhận được từ server
                System.out.println("New account balance: " + value.getBalance());
            }

            @Override
            public void onError(Throwable t) {
                // Xử lý lỗi nếu có
                System.err.println("Error during deposit: " + t.getMessage());
            }

            @Override
            public void onCompleted() {
                // Xử lý khi luồng hoàn thành
                System.out.println("Deposit completed.");
            }
        };

        StreamObserver<DepositRequest> requestObserver = bankServiceStub.deposit(responseObserver); // Tạo StreamObserver để gửi request đến server

        // Gửi account number đầu tiên
        DepositRequest accountRequest = DepositRequest.newBuilder()
                .setAccountNumber(accountNumber)
                .build();
        requestObserver.onNext(accountRequest);

        // Gửi từng phần tiền gửi
        for (double amount : amounts) {
            DepositRequest moneyRequest = DepositRequest.newBuilder()
                    .setMoney(Money.newBuilder().setAmount((int) amount).build())
                    .build();
            requestObserver.onNext(moneyRequest);
        }

        requestObserver.onCompleted(); // Kết thúc luồng gửi request
    }

```

### 4.6.4. Lưu ý khi sử dụng Client Streaming
Client có thể gửi các request đến server một cách liên tục mà không cần chờ phản hồi từ server cho mỗi request.

Server sẽ xử lý tất cả các request và gửi về một response duy nhất khi client hoàn thành việc gửi request.

Đối với luồng client streaming, sử dụng `StreamObserver` để gửi các request và nhận phản hồi từ server, sử dụng mô hình request/response kiểu mới, trong đó:
- Kiểu trả về của phương thức tại `Server` chính là `request stream` của client
- Tham số truyền vào của phương thức tại `Client` chính là `response stream` của server

## 4.7. gRPC Bidirectional Streaming Service
`Bidirectional Streaming` là mô hình giao tiếp trong gRPC mà cả client và server đều có thể gửi và nhận nhiều message một cách độc lập và song song. Cả hai bên có thể gửi message bất cứ lúc nào mà không cần chờ phản hồi từ bên kia. Nó được sử dụng phổ biến ở các case như: Ứng dụng chat thời gian thực, truyền dữ liệu cảm biến theo thời gian thực, hội nghị video, ...

### 4.7.1. Định nghĩa Service bidirectional streaming trong file .proto
```proto
message ChatMessage {
    string user = 1;
    string message = 2;
}

service ChatService {
    rpc Chat(stream ChatMessage) returns (stream ChatMessage); // Định nghĩa phương thức Chat với kiểu request và response đều là stream ChatMessage
}
```

### 4.7.2. Cài đặt Service ở phía Server
Class `ChatService` kế thừa từ `ChatServiceGrpc.ChatServiceImplBase` và override phương thức `Chat`. Trong phương thức này, chúng ta sẽ nhận các message từ client và gửi lại các message đó cho tất cả các client khác (giả lập một phòng chat đơn giản).
```java
@Service
public class ChatService extends ChatServiceGrpc.ChatServiceImplBase {
    private final List<StreamObserver<ChatMessage>> clients = new ArrayList<>(); // Danh sách các client kết nối

    // Override phương thức chat để xử lý bidirectional streaming, truyền vào và trả về StreamObserver<ChatMessage>, kiểu dữ liệu trả về là stream ChatMessage chính là kiểu dữ liệu request từ client
    @Override
    public StreamObserver<ChatMessage> chat(StreamObserver<ChatMessage> responseObserver) {
        clients.add(responseObserver); // Thêm client mới vào danh sách

        return new StreamObserver<ChatMessage>() {
            @Override
            public void onNext(ChatMessage message) {
                // Gửi message nhận được từ client đến tất cả các client khác
                for (StreamObserver<ChatMessage> client : clients) {
                    if (client != responseObserver) { // Không gửi lại cho chính client gửi message
                        client.onNext(message); // Gửi message đến client khác
                    }
                }
            }

            @Override
            public void onError(Throwable t) {
                // Xử lý lỗi nếu có
                clients.remove(responseObserver); // Loại bỏ client khỏi danh sách khi có lỗi
            }

            @Override
            public void onCompleted() {
                // Xử lý khi luồng hoàn thành
                clients.remove(responseObserver); // Loại bỏ client khỏi danh sách khi hoàn thành
                responseObserver.onCompleted(); // Kết thúc luồng cho client
            }
        };
    }
}
```

### 4.7.3. Gọi Service ở phía Client
Giả sử chúng ta đã định nghĩa Channel và stub tương tự như phần 4.3.2, chúng ta sẽ tạo một `StreamObserver<ChatMessage>` để gửi và nhận các message từ server.
```java

     * Gọi phương thức chat từ server gRPC
     * @param user Tên người dùng
     * @param messages Danh sách tin nhắn gửi
     */
    public void chat(String user, List<String> messages) {
        // Tạo StreamObserver để nhận tin nhắn từ server (truyền vào phương thức chat)

            @Override

    }
```

## 5. Valdation và Error Handling trong gRPC
### 5.1. Các loại lỗi phổ biến trong gRPC
Trong gRPC, có một số loại lỗi phổ biến mà bạn có thể gặp phải khi phát triển ứng dụng. Dưới đây là một số loại lỗi thường gặp, sử dụng mã trạng thái đã được define sau khi compile file `code.proto` của package `google.rpc`:
- `OK`: Mã trạng thái 0, biểu thị rằng cuộc gọi gRPC đã thành công mà không có lỗi nào xảy ra. Tương đương với HTTP status code 200.
- `CANCELLED`: Mã trạng thái 1, biểu thị rằng cuộc gọi gRPC đã bị hủy bởi client hoặc server. Tương đương với HTTP status code 499.
- `UNKNOWN`: Mã trạng thái 2, biểu thị rằng đã xảy ra lỗi không xác định trong quá trình xử lý cuộc gọi gRPC. Tương đương với HTTP status code 500.
- `INVALID_ARGUMENT`: Mã trạng thái 3, biểu thị rằng client đã gửi một tham số không hợp lệ trong cuộc gọi gRPC. Tương đương với HTTP status code 400.
- `DEADLINE_EXCEEDED`: Mã trạng thái 4, biểu thị rằng cuộc gọi gRPC đã vượt quá thời gian chờ (deadline) được thiết lập. Tương đương với HTTP status code 504.
- `NOT_FOUND`: Mã trạng thái 5, biểu thị rằng tài nguyên được yêu cầu không tồn tại trên server. Tương đương với HTTP status code 404.
- `ALREADY_EXISTS`: Mã trạng thái 6, biểu thị rằng tài nguyên mà client cố gắng tạo đã tồn tại trên server. Tương đương với HTTP status code 409.
- `PERMISSION_DENIED`: Mã trạng thái 7, biểu thị rằng client không có quyền truy cập vào tài nguyên được yêu cầu. Tương đương với HTTP status code 403.
- `UNAUTHENTICATED`: Mã trạng thái 16, biểu thị rằng client chưa được xác thực để truy cập vào tài nguyên được yêu cầu. Tương đương với HTTP status code 401.
- `RESOURCE_EXHAUSTED`: Mã trạng thái 8, biểu thị rằng tài nguyên trên server đã bị sử dụng hết và không thể xử lý thêm yêu cầu từ client. Tương đương với HTTP status code 429.
- `FAILED_PRECONDITION`: Mã trạng thái 9, biểu thị rằng điều kiện tiên quyết để thực hiện cuộc gọi gRPC không được đáp ứng. Tương đương với HTTP status code 400.
- `ABORTED`: Mã trạng thái 10, biểu thị rằng cuộc gọi gRPC đã bị hủy do xung đột với các cuộc gọi khác. Tương đương với HTTP status code 409.
- `OUT_OF_RANGE`: Mã trạng thái 11, biểu thị rằng giá trị được cung cấp nằm ngoài phạm vi hợp lệ. Tương đương với HTTP status code 400.
- `UNIMPLEMENTED`: Mã trạng thái 12, biểu thị rằng phương thức được gọi không được triển khai trên server. Tương đương với HTTP status code 501.
- `INTERNAL`: Mã trạng thái 13, biểu thị rằng đã xảy ra lỗi nội bộ trên server trong quá trình xử lý cuộc gọi gRPC. Tương đương với HTTP status code 500.
- `UNAVAILABLE`: Mã trạng thái 14, biểu thị rằng dịch vụ gRPC không khả dụng tại thời điểm hiện tại. Tương đương với HTTP status code 503.
- `DATA_LOSS`: Mã trạng thái 15, biểu thị rằng đã xảy ra mất mát dữ liệu không thể khôi phục trong quá trình xử lý cuộc gọi gRPC. Tương đương với HTTP status code 500.

### 5.2. Sử dụng mã trạng thái lỗi trong gRPC, tạo Validation
Để sử dụng các mã trạng thái lỗi này trong gRPC, bạn có thể sử dụng lớp `Status` và `StatusRuntimeException` trong Java sau khi compile, Ví dụ:
```java
import io.grpc.Status;
import io.grpc.StatusRuntimeException;
// Tạo một lỗi với mã trạng thái NOT_FOUND
StatusRuntimeException exception = Status.NOT_FOUND // Sử dụng mã trạng thái NOT_FOUND
    .withDescription("Resource not found") // Thêm mô tả lỗi
    .asRuntimeException(); // Chuyển đổi thành StatusRuntimeException
// Ném lỗi trong phương thức gRPC
throw exception;
```

Ngoài ra, bạn có thể tạo 1 class validation để tái sử dụng trong các service gRPC, ví dụ:
```java
import io.grpc.Status;
import java.util.Optional;

public class RequestValidator {

  /**
   * Validate account number
   * @param accountNumber Số tài khoản
   * @return Optional<Status> - Trả về Optional rỗng nếu hợp lệ, hoặc Optional chứa Status lỗi nếu không hợp lệ
   */
  public static Optional<Status> validateAccount(int accountNumber) {
    if (accountNumber >= 0) {
      return Optional.empty(); // Trả về Optional rỗng nếu hợp lệ
    } else {
      return Optional.of(Status.INVALID_ARGUMENT.withDescription("Account number must be non-negative")); // Trả về lỗi INVALID_ARGUMENT nếu không hợp lệ
    }
  }

  /**
   * Kiểm tra số dư tài khoản có đủ để thực hiện giao dịch hay không
   * @param amount Số tiền cần giao dịch
   * @param balance Số dư tài khoản hiện tại
   * @return Optional<Status> - Trả về Optional rỗng nếu đủ tiền, hoặc Optional chứa Status lỗi nếu không đủ tiền
   */
  public static Optional<Status> isSufficientFunds(int amount, int balance) {
    if (balance >= amount) {
      return Optional.empty(); // Trả về Optional rỗng nếu đủ tiền
    } else {
      return Optional.of(Status.FAILED_PRECONDITION.withDescription("Insufficient funds")); // Trả về lỗi FAILED_PRECONDITION nếu không đủ tiền
    }
  }

}
```

Sau đó, bạn có thể sử dụng class `RequestValidator` này trong các service gRPC ở phía server để validate request, ví dụ:
```java
@Override
public void withdraw(WithdrawRequest request, StreamObserver<Money> responseObserver) {
    int accountNumber = request.getAccountNumber(); // Lấy số tài khoản từ request
    int amount = request.getAmount(); // Lấy số tiền rút từ request
    int balance = accountBalances.getOrDefault(accountNumber, 0.0); // Lấy số dư tài khoản hiện tại (giả lập lấy từ db)

    // Sử dụng RequestValidator để validate account number
    Optional<Status> accountValidation = RequestValidator.validateAccount(accountNumber);
    if (accountValidation.isPresent()) {
        responseObserver.onError(accountValidation.get().asRuntimeException()); // Gửi lỗi nếu không hợp lệ
        return;
    }

    // Sử dụng RequestValidator để kiểm tra số dư tài khoản
    Optional<Status> fundsValidation = RequestValidator.isSufficientFunds(amount, balance);
    if (fundsValidation.isPresent()) {
        responseObserver.onError(fundsValidation.get().asRuntimeException()); // Gửi lỗi nếu không đủ tiền
        return;
    }

    // Tiếp tục xử lý rút tiền nếu hợp lệ
    ...
}
```

Ngoài ra, có thể sử dụng một cách ngắn gọn hơn như sau:
```java
@Override
public void withdraw(WithdrawRequest request, StreamObserver<Money> responseObserver) {
    int accountNumber = request.getAccountNumber(); // Lấy số tài khoản từ request
    int amount = request.getAmount(); // Lấy số tiền rút từ request
    int balance = accountBalances.getOrDefault(accountNumber, 0.0); // Lấy số dư tài khoản hiện tại (giả lập lấy từ db)

    // Validate account number và số dư tài khoản
    RequestValidator.validateAccount(accountNumber) // Validate số tài khoản
        .or(() -> RequestValidator.isSufficientFunds(amount, balance)) // Nếu muốn thêm validate khác, dùng or()
        .map(Status::asRuntimeException) // Chuyển Status thành StatusRuntimeException
        .ifPresentOrElse(
            responseObserver::onError, // Gửi lỗi nếu có
            () -> {
                // Tiếp tục xử lý rút tiền nếu hợp lệ
                ...
            }
        );
}
```

### 5.3. Validation với Trailer Metadata trong gRPC
Trong gRPC, `Trailer Metadata` là một phần của metadata được gửi từ server đến client sau khi hoàn thành cuộc gọi gRPC. Trailer Metadata thường được sử dụng để truyền thông tin bổ sung về kết quả của cuộc gọi, chẳng hạn như mã trạng thái lỗi, thông tin xác thực, hoặc các thông tin khác liên quan đến cuộc gọi.

Trailer Metadata được gửi sau khi tất cả các message response đã được gửi và trước khi kết thúc cuộc gọi gRPC. Client có thể truy cập Trailer Metadata để lấy thông tin bổ sung về cuộc gọi sau khi nhận được tất cả các response. Phù hợp cho việc gửi thông tin lỗi hoặc trạng thái cuối cùng của cuộc gọi.

So với `Status`, `Trailer` cũng cung cấp thông tin về trạng thái của cuộc gọi gRPC, nhưng Trailer Metadata có thể chứa nhiều thông tin hơn và có thể được sử dụng để truyền dữ liệu bổ sung mà không bị giới hạn bởi các mã trạng thái lỗi chuẩn của gRPC.

Vi dụ về cách sử dụng Trailer Metadata trong gRPC sẽ được trình bày trong các phần tiếp theo của bài viết.

#### 5.3.1. Tạo .proto ví dụ
```proto
...

enum ValidationCode {
  INVALID_ACCOUNT = 0;
  INVALID_AMOUNT = 1;
  INSUFFICIENT_BALANCE = 2;
}

message ErrorMessage {
  ValidationCode code = 1;
}
```

#### 5.3.2. Tạo Trailer Metadata trong Server
```java
import io.grpc.Metadata;
import io.grpc.protobuf.ProtoUtils;

public static Metadata toMetadata(ValidationCode code) {
    Metadata metadata = new Metadata(); // Tạo một đối tượng Metadata mới
    // Metadata là mô hình key-value để lưu trữ thông tin bổ sung (Key<T> key, T value) trong gRPC
    Metadata.Key<ErrorMessage> key = ProtoUtils.keyForProto(ErrorMessage.getDefaultInstance()); // Tạo key cho trailer metadata, sử dụng ProtoUtils.keyForProto để tạo key từ message protobuf
    ErrorMessage errorMessage = ErrorMessage.newBuilder() // Tạo đối tượng ErrorMessage
        .setValidationCode(code) // Thiết lập mã validation
        .build();
    metadata.put(key, errorMessage); // Thêm ErrorMessage vào Metadata với key đã tạo

    Metadata.Key<String> stringKey = Metadata.Key.of("error-message", Metadata.ASCII_STRING_MARSHALLER);
    metadata.put(stringKey, code.name()); // Thêm String Metadata để dễ đọc
    return metadata;
}
```

> Các Metadata này sẽ có dạng nhị phân khi được gửi qua mạng, và client có thể giải mã chúng để lấy thông tin lỗi chi tiết. Để sử dụng `String Metadata` cho dễ đọc bạn sử dụng `Metadata.Key.of` thay vì `ProtoUtils.keyForProto` và truyền vào `Metadata.ASCII_STRING_MARSHALLER`, ví dụ:
```java
import io.grpc.Metadata;
Metadata.Key<String> key = Metadata.Key.of("error-message", Metadata.ASCII_STRING_MARSHALLER);
```
#### 5.3.3. Tạo Validation kèm Trailer Metadata trong Server
```java
import io.grpc.Status;
import io.grpc.StatusRuntimeException;
import java.util.Optional;

public class RequestValidator {

  /**
   * Validate account number
   * @param accountNumber Số tài khoản
   * @return Optional<StatusRuntimeException> - Trả về Optional rỗng nếu hợp lệ, hoặc Optional chứa Status lỗi nếu không hợp lệ
   */
  public static Optional<StatusRuntimeException> validateAccount(int accountNumber) {
    if (accountNumber >= 0) {
      return Optional.empty(); // Trả về Optional rỗng nếu hợp lệ
    } else {
      return Optional.of(Status.INVALID_ARGUMENT
      .withDescription("Account number must be non-negative")
      .asRuntimeException(toMetadata(ValidationCode.INVALID_ACCOUNT))); // Trả về lỗi INVALID_ARGUMENT kèm Trailer Metadata nếu không hợp lệ
    }
  }

  /**
   * Kiểm tra số dư tài khoản có đủ để thực hiện giao dịch hay không
   * @param amount Số tiền cần giao dịch
   * @param balance Số dư tài khoản hiện tại
   * @return Optional<StatusRuntimeException> - Trả về Optional rỗng nếu đủ tiền, hoặc Optional chứa Status lỗi nếu không đủ tiền
   */
  public static Optional<StatusRuntimeException> isSufficientFunds(int amount, int balance) {
    if (balance >= amount) {
      return Optional.empty(); // Trả về Optional rỗng nếu đủ tiền
    } else {
      return Optional.of(Status.FAILED_PRECONDITION.withDescription("Insufficient funds")
      .asRuntimeException(toMetadata(ValidationCode.INSUFFICIENT_BALANCE))); // Trả về lỗi FAILED_PRECONDITION kèm Trailer Metadata nếu không đủ tiền
    }
  }

}
```
Sau đó bạn có thể sử dụng class `RequestValidator` này trong các service gRPC ở phía server để validate request, tương tự như phần 5.2.

#### 5.3.4. Lấy Trailer Metadata trong Client
Để lấy Trailer Metadata trong client gRPC, bạn có thể sử dụng `getTrailers()` từ `ClientCall` hoặc từ `StatusRuntimeException` khi có lỗi xảy ra. Dưới đây là ví dụ về cách lấy Trailer Metadata trong client gRPC:
```java
import io.grpc.Metadata;
import io.grpc.StatusRuntimeException;
import io.grpc.protobuf.ProtoUtils;
try {
    // Gọi phương thức gRPC
    ...
} catch (StatusRuntimeException e) {
    Metadata trailers = e.getTrailers(); // Lấy Trailer Metadata từ StatusRuntimeException
    if (trailers != null) {
        // Lấy ErrorMessage từ Trailer Metadata
        Metadata.Key<ErrorMessage> key = ProtoUtils.keyForProto(ErrorMessage.getDefaultInstance());
        ErrorMessage errorMessage = trailers.get(key);
        if (errorMessage != null) {
            // Xử lý ErrorMessage
            System.out.println("Validation code: " + errorMessage.getCode());
        }

        // Lấy String Metadata để dễ đọc
        Metadata.Key<String> stringKey = Metadata.Key.of("error-message", Metadata.ASCII_STRING_MARSHALLER);
        String errorMsg = trailers.get(stringKey);
        if (errorMsg != null) {
            System.out.println("Error message: " + errorMsg);
        }
    }
}
```
> Ngoài cách trên, bạn cũng có thể sử dụng `ClientInterceptor` để tự động xử lý Trailer Metadata cho tất cả các cuộc gọi gRPC trong client. Sẽ nói rõ hơn trong các phần tiếp theo của bài viết.

### 5.4. Sử dụng `oneof` trong Validation
Đôi khi ở phía `Client` không mong muốn nhận bất kỳ `exception` nào từ phía `Server`, thay vào đó chỉ muốn nhận về một `response` với thông tin trả về từ `Server`, có thể là dữ liệu hợp lệ hoặc thông tin lỗi. Trong trường hợp này, chúng ta có thể sử dụng `oneof` trong định nghĩa protobuf để đại diện cho cả hai trường hợp này. Dưới đây là ví dụ về cách sử dụng `oneof` trong định nghĩa protobuf để thực hiện validation:

```proto
message WithdrawResponse {
  oneof response {
    Money money = 1; // Trường hợp thành công
    ErrorMessage error = 2; // Trường hợp lỗi
  }
}
```

Ở phía server, chúng ta sẽ trả về `WithdrawResponse` với trường hợp thành công hoặc lỗi dựa trên kết quả của validation:
```java
@Override
public void withdraw(WithdrawRequest request, StreamObserver<WithdrawResponse> responseObserver) {
    int accountNumber = request.getAccountNumber(); // Lấy số tài khoản từ request
    int amount = request.getAmount(); // Lấy số tiền rút từ request
    int balance = accountBalances.getOrDefault(accountNumber, 0.0); // Lấy số dư tài khoản hiện tại (giả lập lấy từ db)

    WithdrawResponse.Builder responseBuilder = WithdrawResponse.newBuilder(); // Tạo builder cho WithdrawResponse
    if (accountNumber < 0) {
        // Trả về lỗi nếu số tài khoản không hợp lệ
        ErrorMessage errorMessage = ErrorMessage.newBuilder()
            .setCode(ValidationCode.INVALID_ACCOUNT)
            .build();
        responseBuilder.setError(errorMessage);
    } else if (balance < amount) {
        // Trả về lỗi nếu không đủ tiền
        ErrorMessage errorMessage = ErrorMessage.newBuilder()
            .setCode(ValidationCode.INSUFFICIENT_BALANCE)
            .build();
        responseBuilder.setError(errorMessage);
    } else {
        // Xử lý rút tiền nếu hợp lệ
        double newBalance = balance - amount;
        accountBalances.put(accountNumber, newBalance); // Cập nhật số dư tài khoản

        Money money = Money.newBuilder()
            .setAmount(amount)
            .build();
        responseBuilder.setMoney(money);
    }
    WithdrawResponse response = responseBuilder.build(); // Xây dựng WithdrawResponse
    responseObserver.onNext(response); // Gửi phản hồi về client
    responseObserver.onCompleted(); // Kết thúc luồng
}
```

Phía client, chúng ta sẽ kiểm tra trường hợp thành công hoặc lỗi trong `WithdrawResponse`:
```java
public void withdraw(int accountNumber, int amount) {
    WithdrawRequest request = WithdrawRequest.newBuilder()
        .setAccountNumber(accountNumber)
        .setAmount(amount)
        .build();

    WithdrawResponse response = blockingStub.withdraw(request); // Gọi phương thức withdraw từ server gRPC

    // Kiểm tra trường hợp thành công hoặc lỗi
    if (response.hasMoney()) {
        Money money = response.getMoney();
        System.out.println("Withdrawn amount: " + money.getAmount());
    } else if (response.hasError()) {
        ErrorMessage errorMessage = response.getError();
        System.out.println("Error code: " + errorMessage.getCode());
    }
}
```
> Sử dụng `oneof` trong định nghĩa protobuf giúp chúng ta dễ dàng quản lý các trường hợp thành công và lỗi trong cùng một message, đồng thời tránh việc ném exception từ server sang client, giúp giao tiếp giữa hai bên trở nên linh hoạt hơn.

## 6. Deadline xử lý trễ trong gRPC
``Deadline` trong gRPC là một cơ chế cho phép client đặt giới hạn thời gian tối đa mà họ sẵn sàng chờ đợi để nhận phản hồi từ server. Nếu server không thể hoàn thành cuộc gọi gRPC trong khoảng thời gian đã định, cuộc gọi sẽ bị hủy và client sẽ nhận được một lỗi `DEADLINE_EXCEEDED`. Điều này giúp ngăn chặn việc client bị treo hoặc chờ đợi quá lâu khi server gặp sự cố hoặc quá tải.

### 6.1 Sử dụn Deadline với luồng đơn
```java
import io.grpc.Deadline;
// Đặt deadline là 5 giây cho cuộc gọi gRPC
WithdrawResponse response = blockingStub
    .withDeadline(Deadline.after(5, TimeUnit.SECONDS)) // Đặt deadline là 5 giây
    .withdraw(request); // Gọi phương thức withdraw từ server gRPC
```

### 6.2 Sử dụng Deadline với `streaming`
Với các luồng streaming, bạn có thể đặt deadline tương tự như luồng đơn. Tuy nhiên, bạn cần lưu ý rằng deadline sẽ áp dụng cho toàn bộ luồng streaming, bao gồm cả việc gửi và nhận các message.

Để giải quyết vấn đề này, bạn có thể sử dụng `Context` để quản lý deadline trong luồng streaming:

> Đối với `Client Streaming`:
```java
import io.grpc.Context;
// Tạo một Context với deadline là 10 giây
Context contextWithDeadline = Context.current()
    .withDeadlineAfter(10, TimeUnit.SECONDS, ScheduledExecutorService); // Đặt deadline là 10 giây, SheduledExecutorService là một executor để quản lý thời gian
    // Tạo StreamObserver để nhận phản hồi từ server
    StreamObserver<DepositRequest> requestObserver = asyncStub.deposit(responseObserver);
    // Gửi các request đến server 
    ...
```

> Đối với `Server Streaming`, sử dụng `Context.current().isCancelled()` để kiểm tra xem deadline đã hết hạn hay chưa trong quá trình gửi các message:
```java
import io.grpc.Context;
@Override
public void withdraw(WithdrawRequest request, StreamObserver<Money> responseObserver) {
    int accountNumber = request.getAccountNumber();
    int amount = request.getAmount();
    int balance = accountBalances.getOrDefault(accountNumber, 0.0);

    for (int i = 0; i < amount; i += 10) {
        // Kiểm tra xem deadline đã hết hạn hay chưa
        if (Context.current().isCancelled()) {
            System.out.println("Deadline exceeded, stopping the stream.");
            return; // Dừng gửi message nếu deadline đã hết hạn
        }
        Money money = Money.newBuilder()
            .setAmount(Math.min(10, amount - i))
            .build();
        responseObserver.onNext(money); // Gửi message đến client
        try {
            Thread.sleep(1000); // Giả lập thời gian xử lý
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
    responseObserver.onCompleted(); // Kết thúc luồng
}
```

### 6.3. Chờ đợi máy chủ sẵn sàng với `waitForReady`
Trong gRPC, `waitForReady` là một tùy chọn cho phép client chờ đợi cho đến khi máy chủ sẵn sàng để xử lý các cuộc gọi gRPC. Khi `waitForReady` được bật, nếu máy chủ không sẵn sàng (ví dụ: đang khởi động hoặc tạm thời không khả dụng), client sẽ không nhận được lỗi ngay lập tức mà sẽ chờ đợi cho đến khi máy chủ trở nên sẵn sàng hoặc hết thời gian chờ.

Khi máy chủ không khả dụng, nếu `waitForReady` không được bật, client sẽ nhận được lỗi ngay lập tức khi cố gắng thực hiện cuộc gọi gRPC. Tuy nhiên, khi `waitForReady` được bật, client sẽ tiếp tục chờ đợi mà không nhận được lỗi, điều này hữu ích trong các tình huống mà máy chủ có thể tạm thời không khả dụng nhưng sẽ sớm trở lại.

Có thể kết hợp `waitForReady` với `deadline` để đảm bảo rằng client sẽ chờ đợi máy chủ sẵn sàng trong một khoảng thời gian nhất định trước khi hủy cuộc gọi gRPC. Ví dụ:
```java
import io.grpc.Deadline;
// Đặt deadline là 10 giây và bật waitForReady cho cuộc gọi gRPC
WithdrawResponse response = blockingStub
    .withDeadline(Deadline.after(10, TimeUnit.SECONDS)) // Đặt deadline là 10 giây
    .withWaitForReady() // Bật waitForReady để chờ máy chủ sẵn sàng
    .withdraw(request); // Gọi phương thức withdraw từ server gRPC
```

## 7. Tối ưu hóa hiệu suất & Load Balancing trong gRPC
### 7.1. Channel - Khái niệm về kênh kết nối trong gRPC
`Channel` trong gRPC là một khái niệm quan trọng đại diện cho một kết nối mạng giữa client và server gRPC. Nó chịu trách nhiệm quản lý việc gửi và nhận các cuộc gọi gRPC, bao gồm cả việc thiết lập kết nối, quản lý luồng dữ liệu, và xử lý các lỗi mạng và được quản lý bởi `ManagedChannel` trong Java.

Việc tạo kết nối là `Lazy`, nghĩa là kết nối thực sự chỉ được thiết lập khi có cuộc gọi gRPC đầu tiên được thực hiện.

Trong thực tế chỉ cần 1 kênh/kết nối là đủ cho client/server giao tiếp cho nhiều requests đồng thời
- Bạn có thể tạo nhiều kênh - nhưng nó không cần thiết.
- Việc tạo kênh là một quá trình tốn kém tài nguyên, chúng ta tạo khi ứng dụng khởi động và tắt khi ứng dụng dừng hoặc không còn sử dụng nữa.

Đây là một `Thread-safe`, có thể được chia sẻ giữa nhiều luồng trong ứng dụng của bạn.

Có thể chia sẻ vơí nhiều stub để gọi các dịch vụ khác nhau trên cùng một kênh.

### 7.2. Persistent Connections - Kết nối bền vững trong gRPC
Trong gRPC, `Persistent Connections` (kết nối bền vững) đề cập đến việc duy trì một kết nối mạng mở giữa client và server trong suốt thời gian giao tiếp. Điều này có nghĩa là sau khi thiết lập kết nối ban đầu, client và server có thể gửi và nhận nhiều cuộc gọi gRPC mà không cần phải thiết lập lại kết nối mỗi lần.

Kết nối bền vững giúp giảm độ trễ và tăng hiệu suất của các cuộc gọi gRPC, vì việc thiết lập kết nối mới thường tốn thời gian và tài nguyên. Thay vào đó, các cuộc gọi gRPC có thể được gửi qua cùng một kết nối mở, giúp tiết kiệm thời gian và tài nguyên mạng.

Trong suốt quá trình kết nối, PING/PONG được sử dụng để giữ cho kết nối hoạt động và phát hiện các kết nối bị mất. Nếu một bên không nhận được PING trong một khoảng thời gian nhất định, nó có thể giả định rằng kết nối đã bị mất và thực hiện các biện pháp khôi phục kết nối.

### 7.3. Lazy Channel Creation - Tạo kênh kết nối lười biếng trong gRPC
Trong gRPC, `Lazy Channel Creation` (tạo kênh kết nối lười biếng) đề cập đến việc trì hoãn việc thiết lập kết nối mạng giữa client và server cho đến khi có cuộc gọi gRPC đầu tiên được thực hiện. Điều này có nghĩa là kênh kết nối không được tạo ngay khi client khởi tạo, mà chỉ được tạo khi cần thiết.

Việc tạo kênh kết nối lười biếng giúp tiết kiệm tài nguyên mạng và giảm độ trễ khi khởi động ứng dụng, đặc biệt là trong các tình huống mà client có thể không thực hiện bất kỳ cuộc gọi gRPC nào trong một khoảng thời gian dài sau khi khởi động.

### 7.4. Eager Channel Creation - Tạo kênh kết nối nhanh trong gRPC
Trong gRPC, `Eager Channel Creation` (tạo kênh kết nối nhanh) đề cập đến việc thiết lập kết nối mạng giữa client và server ngay khi client khởi tạo, thay vì trì hoãn việc tạo kênh cho đến khi có cuộc gọi gRPC đầu tiên được thực hiện. Điều này có nghĩa là kênh kết nối được tạo ngay lập tức khi client được khởi tạo.

Việc tạo kênh kết nối nhanh giúp giảm độ trễ cho các cuộc gọi gRPC đầu tiên, vì kết nối đã được thiết lập sẵn và sẵn sàng để sử dụng. Điều này đặc biệt hữu ích trong các tình huống mà client dự kiến sẽ thực hiện các cuộc gọi gRPC ngay sau khi khởi động.

Để tạo kênh kết nối nhanh trong gRPC, bạn có thể sử dụng phương thức `getState(true)` của `ManagedChannel`, ví dụ:
```java
ManagedChannel channel = ManagedChannelBuilder.forAddress("localhost", 50051)
    .usePlaintext()
    .build();
// Kích hoạt eager channel creation
channel.getState(true); // Tham số true để kích hoạt eager channel creation 
```
> Lưu ý rằng việc sử dụng eager channel creation có thể tiêu tốn tài nguyên mạng ngay lập tức, vì vậy bạn nên cân nhắc kỹ lưỡng trước khi sử dụng nó trong ứng dụng của mình.

### 7.5. KeepAlive - Giữ kết nối trong gRPC
Trong gRPC, `Server keepAlive` (giữ kết nối máy chủ) đề cập đến việc duy trì kết nối mạng giữa client và server trong suốt thời gian giao tiếp. Điều này giúp đảm bảo rằng kết nối không bị đóng do không hoạt động trong một khoảng thời gian dài.

Khi `keepAlive` được bật, server sẽ gửi các gói tin `PING` định kỳ đến client để giữ cho kết nối hoạt động. Nếu client không phản hồi lại các gói tin `PING` trong một khoảng thời gian nhất định, server có thể giả định rằng kết nối đã bị mất và đóng kết nối.

Dưới đây là một ví dụ về cách cấu hình `keepAlive` trên server gRPC trong Java:
```java
import io.grpc.Server;
import io.grpc.ServerBuilder;
Server server = ServerBuilder.forPort(50051)
    .keepAliveTime(30, TimeUnit.SECONDS) // Thời gian giữa các gói tin PING
    .keepAliveTimeout(10, TimeUnit.SECONDS) // Thời gian chờ phản hồi từ client
    .keepAliveWithoutCalls(true) // Giữ kết nối ngay cả khi không có cuộc gọi gRPC
    .maxConnectionIdle(5, TimeUnit.MINUTES) // Thời gian tối đa kết nối không hoạt động, sau đó sẽ PING đến client để kiểm tra
    .build();
```

Ở phía client, bạn cũng có thể cấu hình `keepAlive` để giữ kết nối với server:
```java
import io.grpc.ManagedChannel;
import io.grpc.ManagedChannelBuilder;
ManagedChannel channel = ManagedChannelBuilder.forAddress("localhost", 50051)
    .usePlaintext()
    .keepAliveTime(30, TimeUnit.SECONDS) // Thời gian giữa các gói tin PING
    .keepAliveTimeout(10, TimeUnit.SECONDS) // Thời gian chờ phản hồi từ server
    .keepAliveWithoutCalls(true) // Giữ kết nối ngay cả khi không có cuộc gọi gRPC
    .build();
```

### 7.6. Load Balancing - Cân bằng tải trong gRPC
`Load Balancing` (cân bằng tải) trong gRPC đề cập đến việc phân phối các cuộc gọi gRPC từ client đến nhiều server để tối ưu hóa hiệu suất và độ tin cậy của hệ thống. Điều này giúp tránh tình trạng quá tải trên một server duy nhất và đảm bảo rằng các yêu cầu được xử lý một cách hiệu quả.

Thông thường, gRPC hỗ trợ nhiều chiến lược cân bằng tải khác nhau, bao gồm:
- `Round Robin`: Phân phối các cuộc gọi gRPC đều đặn giữa các server trong danh sách.
- `Least Connections`: Gửi các cuộc gọi gRPC đến server có ít kết nối hoạt động nhất.
- `Random`: Chọn ngẫu nhiên một server từ danh sách để xử lý cuộc gọi gRPC.

Trên thực tế, mô hình cân bằng tải trong gRPC thường được triển khai thông qua các proxy hoặc load balancer bên ngoài, chẳng hạn như Envoy hoặc NGINX, để quản lý việc phân phối các cuộc gọi gRPC đến các server backend. Ví dụ:
- Ở phía server, bạn có thể triển khai nhiều instance của dịch vụ gRPC và sử dụng một load balancer để phân phối các cuộc gọi đến các instance này.
- Ở phía client, bạn có thể cấu hình để kết nối đến load balancer thay vì kết nối trực tiếp đến các server gRPC.

#### 7.6.1. Ví dụ về cách cấu hình load balancing trong client gRPC
Chúng ta sẽ sử dụng `Nginx` làm load balancer để phân phối các cuộc gọi gRPC đến hai server gRPC backend.

Đầu tiên, cấu hình `Nginx` để làm load balancer cho gRPC:
```nginx.conf
# Không sử dụng localhost. Nó chạy bên trong container. Localhost là chính nó.
# Chúng ta mong muốn container chuyển tiếp các request đến đúng service, vì vậy sử dụng IP của service hoặc tên service trong mạng Docker Compose.
upstream grpc_backend {
    server 10.17.0.2:6565; # Server gRPC instance 1
    server 10.17.0.2:7575; # Server gRPC instance 2
}

server {
    listen 8585 http2; # Nginx lắng nghe trên cổng 8585 với HTTP/2

    # Bất kỳ request nào đến Nginx trên cổng 8585 sẽ được chuyển tiếp đến upstream grpc_backend với giao thức gRPC
    location / {
        grpc_pass grpc://grpc_backend;
    }
}
```

Sử dụng Docker Compose để chạy Nginx và hai instance server gRPC:
```yaml
version: '3'
services:
  nginx:
    image: nginx:1.25-alpine
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro # Gắn file cấu hình Nginx
    ports: 
      - "8585:8585" # Mở cổng 8585 để truy cập từ bên ngoài
```

Tiến hành khởi động Docker Compose:
```bash
docker-compose up -d
```

Trên phía `server`, bạn cần chạy hai instance của server gRPC trên các cổng khác nhau (6565 và 7575).

Trên phía `client`, bạn cấu hình để kết nối đến Nginx load balancer:
```java
import io.grpc.ManagedChannel;
import io.grpc.ManagedChannelBuilder;
ManagedChannel channel = ManagedChannelBuilder.forAddress("localhost", 8585) // Kết nối đến Nginx load balancer
    .usePlaintext()
    .build();
```

#### 7.6.2. Thách thức cân bằng tải trong luồng streaming
Cân bằng tải trong các luồng streaming (như Server Streaming, Client Streaming, và Bi-directional Streaming) có thể gặp một số thách thức nhất định so với các cuộc gọi gRPC đơn giản (Unary RPC). Dưới đây là một số thách thức phổ biến:
- Kết nối lâu dài: Các luồng streaming thường duy trì kết nối lâu dài giữa client và server, điều này có thể làm cho việc cân bằng tải trở nên phức tạp hơn so với các cuộc gọi đơn giản.
- Trạng thái phiên: Trong các luồng streaming, server có thể duy trì trạng thái phiên cho mỗi kết nối, điều này có thể gây khó khăn cho việc chuyển đổi kết nối giữa các server khác nhau trong quá trình streaming.
- Hiệu suất và độ trễ: Việc chuyển đổi kết nối trong các luồng streaming có thể ảnh hưởng đến hiệu suất và độ trễ của ứng dụng, đặc biệt là nếu có nhiều dữ liệu được truyền qua luồng.
- Luồng phân phối không đồng đều: Trong các luồng streaming, việc phân phối luồng dữ liệu không đồng đều giữa các server có thể dẫn đến tình trạng quá tải trên một số server trong khi các server khác lại không được sử dụng hiệu quả.

Để giải quyết những thách thức này, có thể áp dụng các chiến lược sau:
- Sử dụng sticky sessions: Giữ kết nối của client với cùng một server trong suốt thời gian của luồng streaming để tránh việc chuyển đổi kết nối.
- Tối ưu hóa cấu hình load balancer: Điều chỉnh cấu hình của load balancer để xử lý các luồng streaming một cách hiệu quả hơn.
- Giám sát và điều chỉnh: Theo dõi hiệu suất của các luồng streaming và điều chỉnh chiến lược cân bằng tải khi cần thiết để đảm bảo hiệu suất tối ưu.


## 8. Interceptors trong gRPC
### 8.1. Khái niệm Interceptors trong gRPC
`Interceptors` trong gRPC là các thành phần trung gian cho phép bạn can thiệp vào quá trình xử lý các cuộc gọi gRPC, cả ở phía client và server. Chúng hoạt động giống như các bộ lọc hoặc middleware, cho phép bạn thực hiện các hành động bổ sung trước hoặc sau khi một cuộc gọi gRPC được thực hiện.

Interceptors có thể được sử dụng để thực hiện các nhiệm vụ như:
- Ghi log các cuộc gọi gRPC.
- Thêm hoặc sửa đổi metadata trong các cuộc gọi gRPC.
- Thực hiện xác thực và ủy quyền.
- Xử lý lỗi và ngoại lệ.
- Thực hiện các hành động tùy chỉnh khác liên quan đến cuộc gọi gRPC.

> `CallOptions`, `Metadata`, và `Context` trong gRPC đều là các cơ chế để truyền thông tin bổ sung trong quá trình thực hiện các cuộc gọi gRPC, nhưng chúng có những khác biệt quan trọng về mục đích sử dụng và cách thức hoạt động:
> > - `CallOptions`: Được sử dụng để cấu hình các tùy chọn cho cuộc gọi gRPC, chẳng hạn như thiết lập `deadline`, `compression`, và `executor`. `CallOptions` được áp dụng cho toàn bộ cuộc gọi gRPC và ảnh hưởng đến cách thức cuộc gọi được thực hiện. (Ở đầu client)
> > - `Metadata`: Được sử dụng để truyền dữ liệu bổ sung dưới dạng cặp khóa-giá trị (key-value pairs) trong các cuộc gọi gRPC. `Metadata` thường được sử dụng để truyền thông tin như token xác thực, thông tin phiên, hoặc các dữ liệu tùy chỉnh khác giữa client và server. `Metadata` có thể được truy cập và sửa đổi trong các interceptor. (Ở cả client và server)
> > - `Context`: Được sử dụng để truyền thông tin ngữ cảnh (contextual information) trong suốt quá trình thực hiện cuộc gọi gRPC. `Context` cho phép bạn lưu trữ và truy xuất dữ liệu liên quan đến cuộc gọi gRPC, chẳng hạn như thông tin người dùng, trạng thái phiên, hoặc các dữ liệu tùy chỉnh khác. `Context` có thể được sử dụng để chia sẻ dữ liệu giữa các interceptor và các thành phần khác trong quá trình xử lý cuộc gọi gRPC. (Ở server)

### 8.2. Gzip Compression Interceptor
Trong gRPC, `Gzip Compression Interceptor` là một interceptor được sử dụng để nén và giải nén dữ liệu truyền qua các cuộc gọi gRPC bằng thuật toán nén Gzip. Việc sử dụng nén giúp giảm kích thước của dữ liệu được truyền qua mạng, từ đó cải thiện hiệu suất và giảm băng thông sử dụng.

Mặc định, Gzip không được bật trong gRPC, nhưng bạn có thể dễ dàng thêm `Gzip Compression Interceptor` vào cả phía client và server để kích hoạt nén Gzip cho các cuộc gọi gRPC.

Gzip nên được bật khi dữ liệu truyền qua lại giữa Client - Server và Server - Client có kích thước lớn, băng thông hạn chế hoặc khi bạn muốn tối ưu hóa hiệu suất mạng.

Để sử dụng Gzip Compression Interceptor trong gRPC, giống với `Rest` nó cũng cần được chỉ định trong `Header` của request và response.
- grpc-encoding: gzip (Bản tin được nén bằng gzip)
- grpc-accept-encoding: gzip (chấp nhận bản tin nén gzip)

Để thêm Gzip Compression Interceptor trong gRPC, bạn có thể thêm vào `CallOptions` của stub hoặc server builder.

Thêm `CallOptions` trong client:
```java
import io.grpc.CallOptions;
ManagedChannel channel = ManagedChannelBuilder.forAddress("localhost", 50051)
    .usePlaintext()
    .build();
MyServiceGrpc.MyServiceBlockingStub stub = MyServiceGrpc.newBlockingStub(channel)
    .withCallOptions(CallOptions.DEFAULT.withCompression("gzip")); // Bật nén Gzip
// Hoặc sử dụng interceptor
MyServiceGrpc.MyServiceBlockingStub stub = MyServiceGrpc.newBlockingStub(channel)
    .withInterceptors(new ClientGzipInterceptor()); // Thêm Gzip Compression Interceptor
// Hoặc setting mặc định cho toàn bộ kênh
ManagedChannel channel = ManagedChannelBuilder.forAddress("localhost", 50051)
    .usePlaintext()
    .withCompression("gzip") // Bật nén Gzip cho toàn bộ kênh
    .build();
```

Thêm `CallOptions` trong server:
```java
import io.grpc.Server;
// Thêm Gzip Compression Interceptor cho toàn bộ server
Server server = ServerBuilder.forPort(50051)
    .addService(new MyServiceImpl())
    .intercept(new ServerGzipInterceptor()) // Thêm Gzip Compression Interceptor
    .build();

// Hoặc setting mặc định cho toàn bộ server
Server server = ServerBuilder.forPort(50051)
    .addService(new MyServiceImpl())
    .compressorRegistry(CompressorRegistry.newEmptyInstance().register(new GzipCompressor())) // Bật nén Gzip cho toàn bộ server
    .build();

// Hoặc thêm Gzip Compression Interceptor cho từng service
Server server = ServerBuilder.forPort(50051)
    .addService(ServerInterceptors.intercept(new MyServiceImpl(), new ServerGzipInterceptor())) // Thêm Gzip Compression Interceptor cho service cụ thể
    .build();
// Hoặc sử dụng `ServerCallStreamObserver` để bật nén Gzip cho từng cuộc gọi gRPC
@Override
public void myRpcMethod(MyRequest request, StreamObserver<MyResponse> responseObserver) {
    ServerCallStreamObserver<MyResponse> serverCallObserver = (ServerCallStreamObserver<MyResponse>) responseObserver;
    serverCallObserver.setCompression("gzip"); // Bật nén Gzip cho cuộc gọi gRPC cụ thể
    ...
}
```

### 8.3. Call Options - Sử dụng Executor trong gRPC
`Call Options` trong gRPC là một cơ chế cho phép bạn tùy chỉnh các tùy chọn cho các cuộc gọi gRPC, bao gồm việc chỉ định `Executor` để xử lý các cuộc gọi gRPC. Bằng cách sử dụng `Executor`, bạn có thể kiểm soát luồng thực thi của các cuộc gọi gRPC, giúp tối ưu hóa hiệu suất và quản lý tài nguyên trong ứng dụng của bạn.

Để sử dụng `Executor` trong gRPC, bạn có thể thêm nó vào `CallOptions` của stub hoặc server builder.
Thêm `Executor` trong client:
```java
import io.grpc.CallOptions;
import java.util.concurrent.Executor;
import java.util.concurrent.Executors;
Executor myExecutor = Executors.newVirtualThreadPerTaskExecutor(); // Tạo Executor tùy chỉnh

// Hoặc dùng TaskExecutor
// Excutor myExecutor = new ThreadPoolTaskExecutor();
// myExecutor.setCorePoolSize(10);
// myExecutor.setMaxPoolSize(50);
// myExecutor.setQueueCapacity(100);
// myExecutor.initialize();

ManagedChannel channel = ManagedChannelBuilder.forAddress("localhost", 50051)
    .usePlaintext()
    .build();
MyServiceGrpc.MyServiceBlockingStub stub = MyServiceGrpc.newBlockingStub(channel)
    .withCallOptions(CallOptions.DEFAULT.withExecutor(myExecutor)); // Thêm Executor vào CallOptions

// Hoặc setting mặc định cho toàn bộ kênh
ManagedChannel channel = ManagedChannelBuilder.forAddress("localhost", 50051)
    .usePlaintext()
    .executor(myExecutor) // Thêm Executor cho toàn bộ kênh
    .build();
```

### 8.4. Sử dụng Interceptors
`Interceptors` trong gRPC cho phép bạn can thiệp vào quá trình xử lý các cuộc gọi gRPC, cả ở phía client và server.

Có thể sử dụng nhiều `Interceptors` cùng một lúc bằng cách xâu chuỗi chúng lại với nhau hoặc truyền vào một danh sách các `Interceptors`.

`Interceptors` có thể ghi đè các cầu hình đã thiết lập trước đó, và các `Interceptors` cũng có thể ghi đè lẫn nhau tùy thuộc vào thứ tự chúng được thêm vào. Ví dụ, nếu bạn có hai `Interceptors` được thêm vào, `InterceptorA` và `InterceptorB`, và cả hai đều ghi đè cùng một cấu hình, thì cấu hình từ `InterceptorB` sẽ được áp dụng nếu nó được thêm vào sau `InterceptorA`.

#### 8.4.1. Thêm Interceptors trong Client
Để tạo `Interceptors`, bạn cần triển khai giao diện `ClientInterceptor` và ghi đè phương thức `interceptCall()`. Dưới đây là ví dụ về cách tạo một `ClientInterceptor` đơn giản để thiết lập `deadline`
```java
import io.grpc.ClientInterceptor;
import io.grpc.ClientCall;
import io.grpc.Metadata;
import io.grpc.MethodDescriptor;
import io.grpc.ForwardingClientCall;
public class MyClientInterceptor implements ClientInterceptor {
    @Override
    public <ReqT, RespT> ClientCall<ReqT, RespT> interceptCall(
            MethodDescriptor<ReqT, RespT> method, // method chứa thông tin về phương thức gRPC đang được gọi
            CallOptions callOptions, // callOptions chứa các cấu hình cho kênh gọi
            Channel channel // channel đại diện cho kênh kết nối gRPC
    ) {
      callOptions = Objects.nonNull(callOptions.getDeadline())  // Kiểm tra nếu đã có deadline
            ? callOptions   // Giữ nguyên deadline hiện tại
            : callOptions.withDeadlineAfter(5, TimeUnit.SECONDS); // Thiết lập deadline mặc định là 5 giây nếu chưa có
      return channel.newCall(method, callOptions); // Tạo và trả về ClientCall với callOptions đã được cập nhật
    }
}
```

Để thêm `Interceptors` trong client gRPC, bạn có thể sử dụng phương thức `withInterceptors()` của stub hoặc thêm chúng vào `ManagedChannelBuilder`. Dưới đây là ví dụ về cách thêm `Interceptors` trong client gRPC:
```java
import io.grpc.ManagedChannel;
import io.grpc.ManagedChannelBuilder;
ManagedChannel channel = ManagedChannelBuilder.forAddress("localhost", 50051)
    .usePlaintext()
    .build();
MyServiceGrpc.MyServiceBlockingStub stub = MyServiceGrpc.newBlockingStub(channel)
    .withInterceptors(new MyClientInterceptor()); // Thêm Interceptor vào stub
// Hoặc thêm Interceptor vào kênh
ManagedChannel channel = ManagedChannelBuilder.forAddress("localhost", 50051)
    .usePlaintext()
    .intercept(new MyClientInterceptor()) // Thêm Interceptor vào kênh
    .build();
```

#### 8.4.2. Thêm Interceptors trong Server
Để tạo `Interceptors` trong server gRPC, bạn cần triển khai giao diện `ServerInterceptor` và ghi đè phương thức `interceptCall()`. Dưới đây là ví dụ về cách tạo một `ServerInterceptor` đơn giản để set compression gzip:
```java
import io.grpc.ServerInterceptor;
import io.grpc.ServerCall;
import io.grpc.Metadata;
import io.grpc.ForwardingServerCall;
public class MyServerInterceptor implements ServerInterceptor {
    @Override
    public <ReqT, RespT> ServerCall.Listener<ReqT> interceptCall(
            ServerCall<ReqT, RespT> call, // call chứa thông tin về cuộc gọi gRPC đang được xử lý
            Metadata headers, // headers chứa metadata của cuộc gọi gRPC
            ServerCallHandler<ReqT, RespT> serverCallHandler // serverCallHandler đại diện cho hàm xử lý cuộc gọi gRPC
    ) {
        serverCall.setCompression("gzip"); // Thiết lập nén gzip cho cuộc gọi gRPC
        return serverCallHandler.startCall(call, headers); // Tiếp tục xử lý cuộc gọi
    }
}
```

Để thêm `Interceptors` trong server gRPC, bạn có thể sử dụng phương thức `intercept()` của `ServerBuilder` hoặc thêm chúng vào từng service cụ thể. Dưới đây là ví dụ về cách thêm `Interceptors` trong server gRPC:
```java 
import io.grpc.Server;
Server server = ServerBuilder.forPort(50051)
    .addService(new MyServiceImpl())
    .intercept(new MyServerInterceptor()) // Thêm Interceptor vào toàn bộ server
    .build();
// Hoặc thêm Interceptor vào từng service cụ thể
Server server = ServerBuilder.forPort(50051)
    .addService(ServerInterceptors.intercept(new MyServiceImpl(), new MyServerInterceptor())) // Thêm Interceptor vào service cụ thể
    .build();
```

### 8.5. Ứng dụng Interceptors kết hợp với Metadata để truyền key xác thực
Trong gRPC, bạn có thể sử dụng `Interceptors` kết hợp với `Metadata` để truyền thông tin xác thực (authentication) giữa client và server. Dưới đây là ví dụ về cách thực hiện điều này.
#### 8.5.1. Tạo ClientInterceptor để thêm token xác thực vào Metadata
Bạn có thể tạo 1 class kế thừa `ClientInterceptor` để thêm token xác thực vào `Metadata` bằng `ForwardingClientCall` (trình bày sau) hoặc đơn giản sử dụng phương thức tĩnh của `MetadataUtils`.
```java
import io.grpc.ClientInterceptor;
...
Metadata.Key<String> API_TOKEN = Metadata.Key.of("api-token", Metadata.ASCII_STRING_MARSHALLER);
ClientInterceptor authInterceptor = MetadataUtils.newAttachHeadersInterceptor(getAuthHeaders()); // Tạo interceptor để tùy chỉnh Metadata

private Metadata getAuthHeaders() {
    Metadata headers = new Metadata();
    headers.put(API_TOKEN, "your-auth-token"); // Thêm token xác thực vào Metadata
    return headers;
}

// Thêm interceptor vào stub
MyServiceGrpc.MyServiceBlockingStub stub = MyServiceGrpc.newBlockingStub(channel)
    .withInterceptors(authInterceptor); // Thêm Interceptor vào stub

// Hoặc thêm interceptor vào kênh
ManagedChannel channel = ManagedChannelBuilder.forAddress("localhost", 50051)
    .usePlaintext()
    .intercept(authInterceptor) // Thêm Interceptor vào kênh
    .build();
```

#### 8.5.2. Tạo ServerInterceptor để kiểm tra token xác thực từ Metadata
Bạn có thể tạo một class kế thừa `ServerInterceptor` để kiểm tra token xác thực từ `Metadata` trong các cuộc gọi gRPC đến server.
```java
import io.grpc.ServerInterceptor;

public class AuthServerInterceptor implements ServerInterceptor {
    private static final Metadata.Key<String> API_TOKEN = Metadata.Key.of("api-token", Metadata.ASCII_STRING_MARSHALLER);
    @Override
    public <ReqT, RespT> ServerCall.Listener<ReqT> interceptCall(
            ServerCall<ReqT, RespT> call, // call chứa thông tin về cuộc gọi gRPC đang được xử lý
            Metadata headers, // headers chứa metadata của cuộc gọi gRPC
            ServerCallHandler<ReqT, RespT> next // serverCallHandler đại diện cho hàm xử lý cuộc gọi gRPC
    ) {
        String token = headers.get(API_TOKEN); // Lấy token từ Metadata
        if (!isValidToken(token)) { // Kiểm tra tính hợp lệ của token
            call.close(Status.UNAUTHENTICATED.withDescription("Invalid API token"), headers); // Đóng cuộc gọi nếu token không hợp lệ
            return new ServerCall.Listener<ReqT>() {}; // Trả về listener rỗng
        }
        return next.startCall(call, headers); // Tiếp tục xử lý cuộc gọi nếu token hợp lệ
    }
    private boolean isValidToken(String token) {
        // Kiểm tra tính hợp lệ của token (ví dụ: so sánh với giá trị mong đợi)
        return "your-auth-token".equals(token);
    }
}
```

### 8.6. Ứng dụng Interceptors kết hợp với CallCredentials để truyền key xác thực cho Session
Trong gRPC, bạn có thể sử dụng `Interceptors` kết hợp với `CallCredentials` để truyền thông tin xác thực (authentication) giữa client và server. Dưới đây là ví dụ về cách thực hiện điều này.

Sự khác biệt chính giữa `Metadata` và `CallCredentials` là:
- `Metadata` là một cấu trúc dữ liệu dùng để truyền thông tin bổ sung trong các cuộc gọi gRPC, có thể bao gồm các cặp khóa-giá trị (key-value pairs) như token xác thực, thông tin phiên, hoặc các dữ liệu tùy chỉnh khác. `Metadata` thường được sử dụng để truyền thông tin giữa client và server trong quá trình thực hiện cuộc gọi gRPC.
- `CallCredentials` là một cơ chế xác thực trong gRPC, cho phép bạn cung cấp thông tin xác thực cho các cuộc gọi gRPC. `CallCredentials` thường được sử dụng để xác thực client với server, và có thể bao gồm các phương thức xác thực như token, chứng chỉ, hoặc các cơ chế xác thực khác.
#### 8.6.1. Tạo CallCredentials để thêm token xác thực vào CallOptions ở Client
Bạn có thể tạo một class kế thừa `CallCredentials` để thêm token xác thực vào `CallOptions` của các cuộc gọi gRPC từ client.
```java
import io.grpc.CallCredentials;

private static final Metadata.Key<String> API_TOKEN = Metadata.Key.of("Authorization", Metadata.ASCII_STRING_MARSHALLER);

private static class TokenCallCredentials extends CallCredentials { // Tạo class kế thừa CallCredentials
    private final String token; // Biến để lưu trữ token xác thực
    public TokenCallCredentials(String token) { // Constructor để khởi tạo token
        this.token = token;
    }
    // Override phương thức applyRequestMetadata để thêm token vào Metadata
    @Override
    public void applyRequestMetadata(
      RequestInfo requestInfo,  // Thông tin về cuộc gọi gRPC
      Executor appExecutor,  // Executor để thực thi các tác vụ không đồng bộ (nên sử dụng để tránh blocking)
      MetadataApplier applier // Đối tượng để áp dụng Metadata vào cuộc gọi gRPC
    ) { 
        appExecutor.execute(() -> {
            try {
                Metadata headers = new Metadata(); // Tạo Metadata mới
                headers.put(API_TOKEN, "Bearer " + token); // Thêm token xác thực vào Metadata
                applier.apply(headers); // Áp dụng Metadata vào cuộc gọi gRPC
            } catch (Exception e) {
                applier.fail(Status.UNAUTHENTICATED.withCause(e)); // Xử lý lỗi nếu có
            }
        });
    }
    @Override
    public void thisUsesUnstableApi() {
        // Phương thức này được sử dụng để đánh dấu rằng CallCredentials sử dụng API không ổn định
    }

// Sử dụng CallCredentials trong riêng từng stub
MyServiceGrpc.MyServiceBlockingStub stub = MyServiceGrpc.newBlockingStub(channel)
    .withCallCredentials(new TokenCallCredentials("your-auth-token")); // Thêm CallCredentials vào stub
}
```

#### 8.6.2. Tạo ServerInterceptor để kiểm tra token xác thực từ CallOptions ở Server
Bạn có thể tạo một class kế thừa `ServerInterceptor` để kiểm tra token xác thực từ `CallOptions` trong các cuộc gọi gRPC đến server.
```java
import io.grpc.ServerInterceptor;
public class AuthServerInterceptor implements ServerInterceptor {
    private static final Metadata.Key<String> API_TOKEN = Metadata.Key.of("Authorization", Metadata.ASCII_STRING_MARSHALLER);
    @Override
    public <ReqT, RespT> ServerCall.Listener<ReqT> interceptCall(
            ServerCall<ReqT, RespT> call, // call chứa thông tin về cuộc gọi gRPC đang được xử lý
            Metadata headers, // headers chứa metadata của cuộc gọi gRPC
            ServerCallHandler<ReqT, RespT> next // serverCallHandler đại diện cho hàm xử lý cuộc gọi gRPC
    ) {
        String token = headers.get(API_TOKEN); // Lấy token từ Metadata
        if (!isValidToken(token)) { // Kiểm tra tính hợp lệ của token
            call.close(Status.UNAUTHENTICATED.withDescription("Invalid API token"), headers); // Đóng cuộc gọi nếu token không hợp lệ
            return new ServerCall.Listener<ReqT>() {}; // Trả về listener rỗng
        }

        boolean isOneMessage = call.getMethodDescriptor() // Lấy mô tả phương thức gRPC
                                   .getType() // Lấy loại phương thức gRPC
                                   .serverSendsOneMessage(); // Kiểm tra nếu phương thức chỉ gửi một thông điệp tới client
        if (isOneMessage) {
            // Thực hiện các hành động cụ thể cho các phương thức gửi một thông điệp
            return next.startCall(call, headers);
        }
        call.close(Status.PERMISSION_DENIED.withDescription("Only single message methods are allowed"), headers);
        return new ServerCall.Listener<ReqT>() {}; // Trả về listener rỗng
    }
    private boolean isValidToken(String token) {
        // Kiểm tra tính hợp lệ của token (ví dụ: so sánh với giá trị mong đợi)
        return "your-auth-token".equals(token);
    }
}

---
// Thêm interceptor vào server
Server server = ServerBuilder.forPort(50051)
    .addService(new MyServiceImpl())
    .intercept(new AuthServerInterceptor()) // Thêm Interceptor vào toàn bộ server
    .build();
```
> Lưu ý rằng trong ví dụ trên, chúng ta đã kiểm tra xem phương thức gRPC có phải là loại gửi một thông điệp hay không bằng cách sử dụng `call.getMethodDescriptor().getType().serverSendsOneMessage()`. Nếu đúng, chúng ta tiếp tục xử lý cuộc gọi; nếu không, chúng ta đóng cuộc gọi với trạng thái `PERMISSION_DENIED`. Đây là ví dụ minh họa cho Session validation dựa trên loại phương thức gRPC.

### 8.7. Ứng dụng Interceptors kết hợp với Context để lưu trữ thông tin phiên ở Server
Trong gRPC, bạn có thể sử dụng `Interceptors` kết hợp với `Context` để lưu trữ thông tin phiên (session information) giữa các cuộc gọi gRPC ở phía server. Dưới đây là ví dụ về cách thực hiện điều này.
#### 8.7.1. Tạo ServerInterceptor để lưu trữ thông tin phiên vào Context
Bạn có thể tạo một class kế thừa `ServerInterceptor` để lưu trữ thông tin phiên vào `Context` trong các cuộc gọi gRPC đến server.
```java
public enum Role {
  STANDARD,
  PREMIUM;
}
---

import io.grpc.ServerInterceptor;
import io.grpc.Context;
import io.grpc.Metadata;
import io.grpc.ServerCall;
import io.grpc.ServerCallHandler;
  
public class SessionServerInterceptor implements ServerInterceptor {

    public static final Context.Key<Role> ROLE_KEY = Context.key("role"); // Khóa để lưu trữ role trong Context

    @Override
    public <ReqT, RespT> ServerCall.Listener<ReqT> interceptCall(
            ServerCall<ReqT, RespT> call, // call chứa thông tin về cuộc gọi gRPC đang được xử lý
            Metadata headers, // headers chứa metadata của cuộc gọi gRPC
            ServerCallHandler<ReqT, RespT> next // serverCallHandler đại diện cho hàm xử lý cuộc gọi gRPC
    ) {
        String role = headers.get(Metadata.Key.of("Authorization", Metadata.ASCII_STRING_MARSHALLER)); // Lấy role từ Metadata
        Context ctx = Context.current().withValue(ROLE_KEY, Role.valueOf(role)); // Tạo Context mới với role
        if (Objects.nonNull(ctx)) { // Nếu context không null
          return Contexts.interceptCall(ctx, call, headers, next); // Tiếp tục xử lý cuộc gọi với Context mới 
        }
        call.close(Status.UNAUTHENTICATED.withDescription("Invalid role"), headers); // Đóng cuộc gọi nếu role không hợp lệ
        return new ServerCall.Listener<ReqT>() {}; // Trả về listener rỗng
    }
}

    .addService(new MyServiceImpl())

    } else {
```

### 8.8. ForwardingClientCall, ForwardingServerCall
`ForwardingClientCall` và `ForwardingServerCall` là các lớp trừu tượng trong gRPC được sử dụng để tạo các lớp con tùy chỉnh cho việc mở rộng chức năng của các cuộc gọi gRPC ở phía client và server. Chúng cung cấp một cách tiện lợi để chuyển tiếp các cuộc gọi gRPC đến các lớp gốc trong khi vẫn cho phép bạn can thiệp và tùy chỉnh hành vi của cuộc gọi.
- `ForwardingClientCall`: Được sử dụng để tạo các lớp con tùy chỉnh cho các cuộc gọi gRPC ở phía client. Bằng cách kế thừa từ `ForwardingClientCall`, bạn có thể ghi đè các phương thức của cuộc gọi gRPC để thêm các chức năng bổ sung, chẳng hạn như ghi log, thêm metadata, hoặc thực hiện các hành động tùy chỉnh khác trước hoặc sau khi cuộc gọi được thực hiện.
- `ForwardingServerCall`: Được sử dụng để tạo các lớp con tùy chỉnh cho các cuộc gọi gRPC ở phía server. Tương tự như `ForwardingClientCall`, bạn có thể ghi đè các phương thức của cuộc gọi gRPC để thêm các chức năng bổ sung, chẳng hạn như ghi log, kiểm tra xác thực, hoặc thực hiện các hành động tùy chỉnh khác trước hoặc sau khi cuộc gọi được xử lý.

Khi nào sử dụng `ForwardingClientCall` và `ForwardingServerCall`:
- Sử dụng `ForwardingClientCall` khi bạn muốn mở rộng hoặc tùy chỉnh hành vi của các cuộc gọi gRPC ở phía client, chẳng hạn như thêm các interceptor tùy chỉnh hoặc thực hiện các hành động bổ sung trước hoặc sau khi cuộc gọi được thực hiện.
- Sử dụng `ForwardingServerCall` khi bạn muốn mở rộng hoặc tùy chỉnh hành vi của các cuộc gọi gRPC ở phía server, chẳng hạn như thêm các interceptor tùy chỉnh hoặc thực hiện các hành động bổ sung trước hoặc sau khi cuộc gọi được xử lý.

#### 8.8.1. Ví dụ sử dụng ForwardingClientCall để thêm log cho các cuộc gọi gRPC ở phía client
```java
import org.springframework.stereotype.Component;
import brave.Tracer;
import io.grpc.CallOptions;
import io.grpc.Channel;
import io.grpc.ClientCall;
import io.grpc.ClientInterceptor;
import io.grpc.ForwardingClientCall.SimpleForwardingClientCall;
import io.grpc.Metadata;
import io.grpc.MethodDescriptor;
import io.grpc.Status;
import lombok.Getter;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;

@Component
@RequiredArgsConstructor
@Slf4j
public class TracingInterceptor implements ClientInterceptor {

    private final Tracer tracer; // Sử dụng Brave Tracer để lấy thông tin traceID

    private static final Metadata.Key<String> TRACE_ID_KEY = Metadata.Key.of("traceId", Metadata.ASCII_STRING_MARSHALLER); // Khóa để lưu trữ traceId trong Metadata

    // Lớp con của SimpleForwardingClientCall để thêm log và traceId vào các cuộc gọi gRPC
    @Getter
    private static class DescriptorForwardingClientCall<Q, P> extends SimpleForwardingClientCall<Q, P> {

        private final String service; // Tên service gRPC
        private final String operation; // Tên phương thức gRPC

        protected DescriptorForwardingClientCall(
          MethodDescriptor<Q, P> methodDescriptor, // methodDescriptor chứa thông tin về phương thức gRPC đang được gọi
          ClientCall<Q, P> delegate // delegate đại diện cho cuộc gọi gRPC gốc
        ) {
            super(delegate); // Gọi constructor của lớp cha với delegate
            this.service = methodDescriptor.getServiceName(); // Lấy tên service từ methodDescriptor
            this.operation = methodDescriptor.getFullMethodName(); // Lấy tên phương thức đầy đủ từ methodDescriptor
        }
    }

    // Lớp con của ClientCall.Listener để thêm log khi nhận message từ server
    private static class ResponseListener<P> extends ClientCall.Listener<P> {

        private final String service; // Tên service gRPC
        private final String operation; // Tên phương thức gRPC
        private final ClientCall.Listener<P> listener; // listener đại diện cho listener gốc

        protected ResponseListener(String service, String operation, ClientCall.Listener<P> listener) {
            super(); // Gọi constructor của lớp cha
            this.service = service; // Gán tên service
            this.operation = operation; // Gán tên phương thức
            this.listener = listener; // Gán listener gốc
        }

        // Ghi đè phương thức onMessage để thêm log khi nhận message từ server
        @Override
        public void onMessage(P message) {
            log.info("Received gRPC message from {}: [Operation = {}, Message = {}]", service, operation, message);
            listener.onMessage(message);
        }

        // Ghi đè phương thức onHeaders để thêm log khi nhận headers từ server
        @Override
        public void onHeaders(Metadata headers) {
            listener.onHeaders(headers);
        }

        // Ghi đè phương thức onClose để thêm log khi cuộc gọi kết thúc
        @Override
        public void onClose(Status status, Metadata trailers) {
            listener.onClose(status, trailers);
        }

        // Ghi đè phương thức onReady để thêm log khi cuộc gọi sẵn sàng 
        @Override
        public void onReady() {
            listener.onReady();
        }
    }

    // Ghi đè phương thức interceptCall của ClientInterceptor để tùy chỉnh cuộc gọi gRPC
    @Override
    public <Q, P> ClientCall<Q, P> interceptCall(
      MethodDescriptor<Q, P> methodDescriptor,  // methodDescriptor chứa thông tin về phương thức gRPC đang được gọi
      CallOptions callOptions,  // callOptions chứa các cấu hình cho kênh gọi
      Channel channel // channel đại diện cho kênh kết nối gRPC
    ) {
        return new DescriptorForwardingClientCall<>(methodDescriptor, channel.newCall(methodDescriptor, callOptions)) {
            // Ghi đè phương thức sendMessage để thêm log khi gửi message
            @Override
            public void sendMessage(Q message) {
                log.info("Send gRPC message to {}: [Operation = {}, Message = {}]", getService(), getOperation(), message);
                super.sendMessage(message); // Gọi phương thức gốc để gửi message
            }

            // Ghi đè phương thức start để thêm traceId vào Metadata khi bắt đầu cuộc gọi
            @Override
            public void start(Listener<P> responseListener, Metadata headers) {
                headers.put(TRACE_ID_KEY, traceId()); // Thêm traceId vào Metadata
                ResponseListener<P> listener = new ResponseListener<>(getService(), getOperation(), responseListener); // Tạo ResponseListener để thêm log khi nhận message từ server
                super.start(listener, headers); // Gọi phương thức gốc để bắt đầu cuộc gọi
            }
        };
    }

    // Phương thức lấy traceId hiện tại hoặc tạo mới nếu không có
    private String traceId() {
        return tracer.currentSpan() != null ? tracer.currentSpan().context().traceIdString() : tracer.newTrace().context().traceIdString();
    }
```

#### 8.8.2. Ví dụ sử dụng ForwardingServerCall để thêm log cho các cuộc gọi gRPC ở phía server
```java
import io.grpc.ServerCall;
import io.grpc.ServerCallHandler;
import io.grpc.ServerInterceptor;
import io.grpc.ForwardingServerCall.SimpleForwardingServerCall;
import io.grpc.Metadata;
import io.grpc.Status;
import lombok.extern.slf4j.Slf4j;
@Slf4j
public class LoggingServerInterceptor implements ServerInterceptor {

    // Lớp con của SimpleForwardingServerCall để thêm log cho các cuộc gọi gRPC
    private static class DescriptorForwardingServerCall<ReqT, RespT> extends SimpleForwardingServerCall<ReqT, RespT> {

        private final String service; // Tên service gRPC
        private final String operation; // Tên phương thức gRPC

        protected DescriptorForwardingServerCall(
          ServerCall<ReqT, RespT> delegate // delegate đại diện cho cuộc gọi gRPC gốc
        ) {
            super(delegate); // Gọi constructor của lớp cha với delegate
            this.service = delegate.getMethodDescriptor().getServiceName(); // Lấy tên service từ methodDescriptor
            this.operation = delegate.getMethodDescriptor().getFullMethodName(); // Lấy tên phương thức đầy đủ từ methodDescriptor
        }

        // Ghi đè phương thức sendMessage để thêm log khi gửi message
        @Override
        public void sendMessage(RespT message) {
            log.info("Send gRPC message to {}: [Operation = {}, Message = {}]", service, operation, message);
            super.sendMessage(message); // Gọi phương thức gốc để gửi message
        }

        // Ghi đè phương thức close để thêm log khi cuộc gọi kết thúc
        @Override
        public void close(Status status, Metadata trailers) {
            log.info("gRPC call to {} ended: [Operation = {}, Status = {}]", service, operation, status);
            super.close(status, trailers); // Gọi phương thức gốc để đóng cuộc gọi
        }
    }

    // Lớp con của ServerCall.Listener để thêm log khi nhận message từ client
    private static class RequestListener<ReqT> extends ServerCall.Listener<ReqT> {

        private final ServerCall.Listener<ReqT> listener; // listener đại diện cho listener gốc

        protected RequestListener(ServerCall.Listener<ReqT> listener) {
            super(); // Gọi constructor của lớp cha
            this.listener = listener; // Gán listener gốc
        }

        // Ghi đè phương thức onMessage để thêm log khi nhận message từ client
        @Override
        public void onMessage(ReqT message) {
            log.info("Received gRPC message from {}: [Operation = {}, Message = {}]", service, operation, message);
            listener.onMessage(message);
        }

        // Ghi đè phương thức onHalfClose để thêm log khi client kết thúc gửi message
        @Override
        public void onHalfClose() {
            listener.onHalfClose();
        }

        // Ghi đè phương thức onCancel để thêm log khi cuộc gọi bị hủy
        @Override
        public void onCancel() {
            listener.onCancel();
        }

        // Ghi đè phương thức onComplete để thêm log khi cuộc gọi hoàn thành
        @Override
        public void onComplete() {
            listener.onComplete();
        }

        // Ghi đè phương thức onReady để thêm log khi cuộc gọi sẵn sàng 
        @Override
        public void onReady() {
            listener.onReady();
        }
    }

    // Ghi đè phương thức interceptCall của ServerInterceptor để tùy chỉnh cuộc gọi gRPC
    @Override
    public <ReqT, RespT> ServerCall.Listener<ReqT> interceptCall(
      ServerCall<ReqT, RespT> call,  // call chứa thông tin về cuộc gọi gRPC đang được xử lý
      Metadata headers,  // headers chứa metadata của cuộc gọi gRPC
      ServerCallHandler<ReqT, RespT> next // serverCallHandler đại diện cho hàm xử lý cuộc gọi gRPC
    ) {
        String methodName = call.getMethodDescriptor().getFullMethodName(); // Lấy tên phương thức đầy đủ từ methodDescriptor
        log.info("Received gRPC call: [Method = {}]", methodName); // Ghi log khi nhận cuộc gọi gRPC
        return new RequestListener<>( // Trả về RequestListener để thêm log khi nhận message từ client
          next.startCall(new DescriptorForwardingServerCall<>(call.getMethodDescriptor().getServiceName(), call.getMethodDescriptor().getFullMethodName(), call), headers) // Tạo DescriptorForwardingServerCall để thêm log cho cuộc gọi gRPC
        ); // Gọi phương thức gốc để bắt đầu cuộc gọi
    }
}
```

## 9. SSL/TLS - Bảo mật kênh gRPC
gRPC hỗ trợ SSL/TLS để bảo mật kênh truyền thông giữa client và server. Giống như các giao thức truyền thông khác, SSL/TLS cung cấp mã hóa dữ liệu và xác thực giữa các bên tham gia giao tiếp. Dưới đây là cách cấu hình SSL/TLS cho gRPC trong Spring Boot.
### 9.1. Tạo chứng chỉ SSL/TLS (KeyStore và TrustStore)
Để sử dụng SSL/TLS trong gRPC, bạn cần tạo chứng chỉ SSL/TLS cho server và client. Bạn có thể sử dụng `keytool` để tạo KeyStore và TrustStore. Dưới đây là ví dụ về cách tạo KeyStore và TrustStore:
```bash
#!/bin/bash

# Tạo root CA certificate và private key
openssl genrsa -out root.key
openssl req -new -x509 -key root.key -out root.crt  -subj "/CN=localhost" -nodes

# keystore
keytool -keystore grpc.keystore.jks -storepass changeit -alias localhost -validity 3650 -genkey -keyalg RSA -dname "CN=localhost"

# Tạo CSR (Certificate Signing Request)
keytool -keystore grpc.keystore.jks -storepass changeit -alias localhost -certreq -file grpc-signing-request.crt

# CA ký CSR để tạo certificate cho server
openssl x509 -req -CA root.crt -CAkey root.key -in grpc-signing-request.crt -out grpc-signed.crt -days 3650 -CAcreateserial
te

# Chúng ta import cả root CA và certificate đã ký vào keystore
keytool -keystore grpc.keystore.jks -storepass changeit -alias CARoot -import -file root.crt -noprompt
keytool -keystore grpc.keystore.jks -storepass changeit -alias localhost -import -file grpc-signed.crt -noprompt

# Tạo truststore và import root CA vào truststore và đưa vào client sử dụng
keytool -keystore grpc.truststore.jks -storepass changeit -noprompt -alias CARoot -import -file root.crt
```

Sau khi chạy script trên, bạn sẽ có hai file:
- `grpc.keystore.jks`: Chứa chứng chỉ và khóa riêng của server.
- `grpc.truststore.jks`: Chứa chứng chỉ root CA để client tin tưởng server.
- `storepass`: Mật khẩu cho cả KeyStore và TrustStore trong ví dụ trên là `changeit`. Bạn có thể thay đổi mật khẩu này theo nhu cầu của bạn.

### 9.2. Thiết lập KeyStore/TrustStore vào ManagerFactory
Để thiết lập KeyStore và TrustStore vào `KeyManagerFactory` và `TrustManagerFactory`, bạn có thể sử dụng đoạn mã sau trong ứng dụng Spring Boot của bạn:
```java
import java.nio.file.Path;

import java.io.InputStream;
import java.nio.file.Files;
import java.security.KeyStore;
import io.grpc.netty.shaded.io.grpc.netty.GrpcSslContexts;
import io.grpc.netty.shaded.io.netty.handler.ssl.SslContext;
import io.grpc.netty.shaded.io.netty.handler.ssl.SslContextBuilder;
import io.grpc.netty.shaded.io.grpc.netty.NettyChannelBuilder;
import javax.net.ssl.KeyManagerFactory;
import javax.net.ssl.TrustManagerFactory;


...
private static final Path KEYSTORE_PATH = Paths.get("path/to/grpc.keystore.jks"); // Đường dẫn tới file KeyStore
private static final Path TRUSTSTORE_PATH = Paths.get("path/to/grpc.truststore.jks"); // Đường dẫn tới file TrustStore
private static final char[] STORE_PASSWORD = "changeit".toCharArray(); // Mật khẩu cho KeyStore và TrustStore

// Chỉ tạo trên client
protected SslContext clientSslContext() throws Exception {
  return GrpcSslContexts.configure(
    SslContextBuilder.forClient()) // Tạo SslContextBuilder cho client
                     .trustManager(getTrustManagerFactory()).build(); // Cấu hình TrustManagerFactory cho client
}

// Tạo TrustManagerFactory từ TrustStore
protected TrustManagerFactory getTrustManagerFactory() throws Exception {
  KeyStore trustStore = KeyStore.getInstance(KeyStore.getDefaultType()); // Tạo instance KeyStore với loại mặc định
  try (InputStream trustStoreStream = Files.newInputStream(TRUSTSTORE_PATH)) {
    trustStore.load(trustStoreStream, STORE_PASSWORD); // Load TrustStore từ file
  }
  TrustManagerFactory trustManagerFactory = TrustManagerFactory.getInstance(TrustManagerFactory.getDefaultAlgorithm()); // Tạo TrustManagerFactory với thuật toán mặc định
  trustManagerFactory.init(trustStore); // Khởi tạo TrustManagerFactory với TrustStore
  return trustManagerFactory; // Trả về TrustManagerFactory
}

// Sử dụng SslContext trong kênh gRPC của client
ManagedChannel channel = NettyChannelBuilder.forAddress("localhost", 50051) // Buộc phải dùng NettyChannelBuilder để hỗ trợ SSL/TLS thay vì ManagedChannelBuilder
    .sslContext(clientSslContext()) // Cấu hình SslContext cho client
    .build();

// Chỉ tạo trên server
protected SslContext serverSslContext() throws Exception {
  return GrpcSslContexts.configure( 
    SslContextBuilder.forServer(getKeyManagerFactory())) //  Tạo SslContextBuilder cho server với KeyManagerFactory
                     .trustManager(getTrustManagerFactory()).build(); // Cấu hình TrustManagerFactory cho server
}

// Tạo KeyManagerFactory từ KeyStore
protected KeyManagerFactory getKeyManagerFactory() throws Exception {
  KeyStore keyStore = KeyStore.getInstance(KeyStore.getDefaultType());
  try (InputStream keyStoreStream = Files.newInputStream(KEYSTORE_PATH)) {
    keyStore.load(keyStoreStream, STORE_PASSWORD); // Load KeyStore từ file
  }
  KeyManagerFactory keyManagerFactory = KeyManagerFactory.getInstance(KeyManagerFactory.getDefaultAlgorithm()); // Tạo KeyManagerFactory với thuật toán mặc định
  keyManagerFactory.init(keyStore, STORE_PASSWORD); // Khởi tạo KeyManagerFactory với KeyStore và mật khẩu
  return keyManagerFactory; // Trả về KeyManagerFactory
}

// Sử dụng SslContext trong kênh gRPC của server
Server server = NettyServerBuilder.forPort(50051)
    .sslContext(serverSslContext()) // Cấu hình SslContext cho server
```

## 10.2. Định nghĩa gRPC Service với Protobuf

### 10.2.1. Tạo file schema.proto

File `.proto` là file định nghĩa giao thức gRPC bằng ngôn ngữ Protocol Buffers. Dưới đây là các bước để tạo một file `.proto` trong dự án Spring Boot:

1. Đầu tiên, tạo thư mục `proto/src/main/proto` trong dự án của bạn.
2. Tạo file `schema.proto` trong thư mục đó với nội dung như sau:

```proto
syntax = "proto3"; // Khai báo sử dụng phiên bản proto3

package com.didan; // Đặt tên package cho file proto

option java_multiple_files = true; // Tạo nhiều file Java từ một file proto

// Định nghĩa message Book
message Book {
  int32 book_id = 1; // ID của sách (số thứ tự 1)
  string title = 2;  // Tiêu đề sách (số thứ tự 2)
  float price = 3;   // Giá sách (số thứ tự 3)
  int32 pages = 4;   // Số trang (số thứ tự 4)
  int32 author_id = 5; // ID tác giả (số thứ tự 5)
}

// Định nghĩa message Author
message Author {
  int32 author_id = 1;  // ID tác giả
  string first_name = 2; // Tên tác giả
  string last_name = 3;  // Họ tác giả
  string gender = 4;     // Giới tính
  int32 book_id = 5;     // ID sách
}

// Định nghĩa service BookAuthorService
service BookAuthorService {
  // Phương thức unary (1 request, 1 response)
  rpc getAuthor(Author) returns(Author) {}
}
```

### 10.2.2. Chi tiết cú pháp file .proto

#### Cú pháp cơ bản

- `syntax = "proto3"`: Khai báo sử dụng phiên bản Protocol Buffers 3.
- `package com.didan`: Định nghĩa namespace để tránh xung đột tên.
- `option java_multiple_files = true`: Tạo file Java riêng cho mỗi message và service.

#### Message

Message là cấu trúc dữ liệu chính trong Protocol Buffers. Mỗi trường trong message được định nghĩa với cú pháp:

```proto
<kiểu_dữ_liệu> <tên_trường> = <số_thứ_tự>;
```

- **Kiểu dữ liệu**: int32, int64, float, double, bool, string, bytes, enum, message khác,...
- **Tên trường**: Tên của trường (nên sử dụng snake_case).
- **Số thứ tự**: Số nguyên dương duy nhất cho mỗi trường trong message, dùng để định danh trường trong quá trình serialize/deserialize.

#### Service

Service định nghĩa các phương thức RPC mà client có thể gọi:

```proto
service <TênService> {
  rpc <TênPhươngThức>(<KiểuRequest>) returns (<KiểuResponse>) {}
}
```

#### Các kiểu RPC

1. **Unary RPC**: Client gửi một request, server trả về một response.
   ```proto
   rpc getAuthor(Author) returns(Author) {}
   ```

2. **Server Streaming RPC**: Client gửi một request, server trả về nhiều response.
   ```proto
   rpc listAuthors(Author) returns(stream Author) {}
   ```

3. **Client Streaming RPC**: Client gửi nhiều request, server trả về một response.
   ```proto
   rpc createAuthors(stream Author) returns(Author) {}
   ```

4. **Bidirectional Streaming RPC**: Client và server đều gửi nhiều message.
   ```proto
   rpc chatWithAuthor(stream Author) returns(stream Author) {}
   ```

### 10.2.5. Các file Java được tạo ra sau khi biên dịch

Khi biên dịch file `.proto` có nội dung như trên, các file Java sau sẽ được tạo ra trong thư mục `target/generated-sources/protobuf`:

1. **Message classes**:
   - `Book.java`: Class cho message Book.
   - `BookOrBuilder.java`: Interface cho Book builder.
   - `Author.java`: Class cho message Author.
   - `AuthorOrBuilder.java`: Interface cho Author builder.

2. **Service classes**:
   - `BookAuthorServiceGrpc.java`: Class chứa code để gọi service, bao gồm:
     - `BookAuthorServiceImplBase`: Abstract class để implement service trên server.
     - `BookAuthorServiceBlockingStub`: Stub để gọi service một cách đồng bộ.
     - `BookAuthorServiceFutureStub`: Stub để gọi service với Future.
     - `BookAuthorServiceStub`: Stub để gọi service một cách bất đồng bộ.

### 10.2.6. Best practices khi viết file .proto

1. **Số thứ tự trường**:
   - Sử dụng số từ 1-15 cho các trường thường xuyên được sử dụng (chỉ tốn 1 byte).
   - Số từ 16-2047 tốn 2 bytes.
   - Không sử dụng lại số thứ tự, ngay cả khi trường đã bị xóa.

2. **Tên trường**:
   - Sử dụng snake_case cho tên trường trong file .proto.
   - Protobuf compiler sẽ tự động chuyển thành camelCase trong code Java.

3. **Phiên bản**:
   - Thêm phiên bản vào tên package để hỗ trợ tương thích ngược.
   - Ví dụ: `package com.didan.v1;`

4. **Reserved Fields**:
   - Khi xóa một trường, đánh dấu số của nó là reserved để tránh tái sử dụng.
   ```proto
   message Book {
     reserved 4, 15, 16 to 20;
     reserved "removed_field";
   }
   ```

5. **Default Values**:
   - Khi một trường không được set, nó sẽ có giá trị mặc định (0, chuỗi rỗng, false).
   - Không thể phân biệt giữa giá trị mặc định và giá trị được set.

### 10.2.7. Ví dụ mở rộng

Ví dụ về việc sử dụng các tính năng nâng cao của Protocol Buffers:

```proto
syntax = "proto3";

package com.didan.v1;

option java_multiple_files = true;
option java_package = "com.didan.model";
option java_outer_classname = "BookProtos";

import "google/protobuf/timestamp.proto";

// Định nghĩa enum cho thể loại sách
enum BookCategory {
  UNKNOWN = 0;
  FICTION = 1;
  SCIENCE = 2;
  BIOGRAPHY = 3;
  TECHNOLOGY = 4;
}

message Book {
  int32 book_id = 1;
  string title = 2;
  float price = 3;
  int32 pages = 4;
  int32 author_id = 5;
  BookCategory category = 6;
  google.protobuf.Timestamp published_date = 7;
  
  // Nested message - Thông tin nhà xuất bản
  message Publisher {
    string name = 1;
    string address = 2;
  }
  
  Publisher publisher = 8;
  
  // Repeated field - Danh sách từ khóa
  repeated string keywords = 9;
}

// Request/Response messages
message GetBookRequest {
  int32 book_id = 1;
}

message GetBookResponse {
  Book book = 1;
  string message = 2;
  int32 status_code = 3;
}

// Service với nhiều phương thức
service BookService {
  // Unary
  rpc GetBook(GetBookRequest) returns(GetBookResponse) {}
  
  // Server streaming
  rpc ListBooks(GetBookRequest) returns(stream Book) {}
  
  // Client streaming
  rpc CreateBooks(stream Book) returns(GetBookResponse) {}
  
  // Bidirectional streaming
  rpc ProcessBooks(stream Book) returns(stream GetBookResponse) {}
}
```

### 11.4. Triển khai gRPC Service

Để triển khai một gRPC service, bạn cần tạo một class kế thừa từ abstract class được tự động tạo ra từ file `.proto`. Trong trường hợp này, chúng ta sẽ triển khai `BookAuthorServiceGrpc.BookAuthorServiceImplBase`. Đây là class cơ sở để bạn override các phương thức RPC đã định nghĩa trong file `.proto`.

Các phương thức RPC mặc định sẽ có kiểu trả về `void` và nhận vào các tham số như request object và một `StreamObserver` để gửi response. Tuy là `void`, nhưng bạn sẽ sử dụng `StreamObserver` để gửi dữ liệu trả về cho client theo dạng `stream`.

```java
package com.didan.server.service;

import com.didan.Author;
import com.didan.BookAuthorServiceGrpc;
import io.grpc.stub.StreamObserver;
import net.devh.boot.grpc.server.service.GrpcService;

@GrpcService
public class BookAuthorServerService extends BookAuthorServiceGrpc.BookAuthorServiceImplBase {

    @Override // Override phương thức getAuthor từ file .proto 
    public void getAuthor(Author request, StreamObserver<Author> responseObserver) {
        // Xử lý yêu cầu và tạo phản hồi
        System.out.println("Server received request for author ID: " + request.getAuthorId());
        
        // Tạo đối tượng Author để trả về
        Author response = Author.newBuilder()
                .setAuthorId(request.getAuthorId())
                .setFirstName("Nguyễn")
                .setLastName("Văn A")
                .setGender("Nam")
                .setBookId(123)
                .build();
        
        // Gửi response về client
        responseObserver.onNext(response);
        
        // Hoàn thành xử lý
        responseObserver.onCompleted();
    }
}
```

Annotation `@GrpcService` đánh dấu class này là một gRPC service và tự động đăng ký nó với gRPC server.

### 11.5. Tạo server streaming service

```java
@GrpcService
public class BookAuthorServerService extends BookAuthorServiceGrpc.BookAuthorServiceImplBase {

    // Phương thức unary đã triển khai ở trên

    @Override
    public void listAuthors(Author request, StreamObserver<Author> responseObserver) {
        System.out.println("Server received request to list authors with book ID: " + request.getBookId());

        for (int i = 1; i <= 5; i++) {
            Author author = Author.newBuilder()
                .setAuthorId(100 + i)
                .setFirstName("Tác giả")
                .setLastName("Số " + i)

                .setBookId(request.getBookId())
                .build();

            }
        }
```

### 11.6. Tạo client streaming service

```java
@GrpcService
public class BookAuthorServerService extends BookAuthorServiceGrpc.BookAuthorServiceImplBase {

    // Các phương thức đã triển khai ở trên
    // ...
    
    @Override
    public StreamObserver<Author> createAuthors(StreamObserver<Author> responseObserver) {
        return new StreamObserver<Author>() {
            private int count = 0;
            private Author lastAuthor = null;
            
            @Override
            public void onNext(Author author) {
                // Xử lý mỗi author được gửi từ client
                count++;
                System.out.println("Received author #" + count + ": " + author.getFirstName() + " " + author.getLastName());
                lastAuthor = author;
            }
            
            @Override
            public void onError(Throwable t) {
                // Xử lý lỗi
                System.err.println("Error in createAuthors: " + t.getMessage());
            }
            
            @Override
            public void onCompleted() {
                // Khi client hoàn thành việc gửi dữ liệu
                System.out.println("Client completed sending data. Total authors received: " + count);
                
                // Gửi response về client
                Author response;
                if (lastAuthor != null) {
                    response = Author.newBuilder(lastAuthor)
                            .setFirstName("Processed " + count + " authors")
                            .build();
                } else {
                    response = Author.newBuilder()
                            .setAuthorId(-1)
                            .setFirstName("No authors received")
                            .build();
                }
                
                responseObserver.onNext(response);
                responseObserver.onCompleted();
            }
        };
    }
}
```

#### 11.8.4. Cập nhật Service để sử dụng Repository

```java
package com.didan.server.service;

import com.didan.Author;
import com.didan.BookAuthorServiceGrpc;
import com.didan.server.entity.AuthorEntity;
import com.didan.server.repository.AuthorRepository;
import io.grpc.Status;
import io.grpc.stub.StreamObserver;
import net.devh.boot.grpc.server.service.GrpcService;
import org.springframework.beans.factory.annotation.Autowired;

import java.util.Optional;

@GrpcService
public class BookAuthorServerService extends BookAuthorServiceGrpc.BookAuthorServiceImplBase {

    private final AuthorRepository authorRepository;
    
    @Autowired
    public BookAuthorServerService(AuthorRepository authorRepository) {
        this.authorRepository = authorRepository;
    }

    @Override
    public void getAuthor(Author request, StreamObserver<Author> responseObserver) {
        try {
            if (request.getAuthorId() <= 0) {
                // Xử lý lỗi nếu ID không hợp lệ
                responseObserver.onError(
                    Status.INVALID_ARGUMENT
                        .withDescription("Author ID must be positive")
                        .asRuntimeException()
                );
                return;
            }
            
            // Tìm author từ database
            Optional<AuthorEntity> optionalAuthor = authorRepository.findById(request.getAuthorId());
            
            if (optionalAuthor.isPresent()) {
                AuthorEntity entity = optionalAuthor.get();
                
                // Chuyển đổi từ entity sang protobuf message
                Author response = Author.newBuilder()
                        .setAuthorId(entity.getId())
                        .setFirstName(entity.getFirstName())
                        .setLastName(entity.getLastName())
                        .setGender(entity.getGender())
                        .setBookId(entity.getBookId())
                        .build();
                
                // Gửi response về client
                responseObserver.onNext(response);
                responseObserver.onCompleted();
            } else {
                // Xử lý khi không tìm thấy author
                responseObserver.onError(
                    Status.NOT_FOUND
                        .withDescription("Author not found with ID: " + request.getAuthorId())
```

Tạo một Interceptor để xác thực các yêu cầu gRPC:

```java
package com.didan.server.interceptor;

import io.grpc.*;
import net.devh.boot.grpc.server.interceptor.GrpcGlobalServerInterceptor;
import org.springframework.stereotype.Component;

@Component
@GrpcGlobalServerInterceptor
public class AuthInterceptor implements ServerInterceptor {

    private static final Metadata.Key<String> AUTH_TOKEN_KEY =
            Metadata.Key.of("Authorization", Metadata.ASCII_STRING_MARSHALLER);

    @Override
    public <ReqT, RespT> ServerCall.Listener<ReqT> interceptCall(
            ServerCall<ReqT, RespT> call,
            Metadata headers,
            ServerCallHandler<ReqT, RespT> next) {
        
        String token = headers.get(AUTH_TOKEN_KEY);
        
        if (token == null || !isValidToken(token)) {
            call.close(Status.UNAUTHENTICATED
                    .withDescription("Invalid or missing token"),
                    new Metadata());
                    
            return new ServerCall.Listener<>() {};
        }
        
        return next.startCall(call, headers);
    }
    
    private boolean isValidToken(String token) {
        // Logic kiểm tra token
        // Trong thực tế, bạn có thể sử dụng JWT hoặc OAuth2
        return token.startsWith("Bearer ") && token.length() > 10;
    }
}
```

```java
            ServerCall<ReqT, RespT> call,

                                methodName, status.getCode());
                        super.close(status, trailers);
                    }
                }, headers)) {
            
            @Override
            public void onMessage(ReqT message) {
                logger.info("Received message: {}", message);
                super.onMessage(message);
            }
            
            @Override
            public void onHalfClose() {
                logger.info("Client finished sending messages for method: {}", methodName);
                super.onHalfClose();
            }
            
            @Override
            public void onComplete() {
                logger.info("Call completed for method: {}", methodName);
                super.onComplete();
            }
            
            @Override
```

## 13. So sánh các phương thức gRPC

| Kiểu RPC | Mô tả | Use cases |
|----------|-------|-----------|
| Unary | Client gửi một request và nhận về một response | Hầu hết các API thông thường, như get/update/delete |
| Server Streaming | Client gửi một request và nhận về nhiều response | Lấy dữ liệu lớn, real-time updates, streaming data |
| Client Streaming | Client gửi nhiều request và nhận về một response | Tải lên dữ liệu lớn, real-time data collection |
| Bidirectional Streaming | Client và server gửi và nhận nhiều message | Chat applications, real-time collaboration, monitoring |

### 13.1. Ví dụ Unary RPC

**Schema.proto**:
```proto
rpc GetAuthor(AuthorRequest) returns (Author) {}
```

**Server implementation**:
```java
@Override
public void getAuthor(AuthorRequest request, StreamObserver<Author> responseObserver) {
    Author author = // ... logic to get author
    responseObserver.onNext(author);
    responseObserver.onCompleted();
}
```

**Client implementation**:
```java
AuthorRequest request = AuthorRequest.newBuilder().setAuthorId(123).build();
Author response = stub.getAuthor(request);
```

### 13.2. Ví dụ Server Streaming RPC

**Schema.proto**:
```proto
rpc ListAuthors(BookRequest) returns (stream Author) {}
```

**Server implementation**:
```java
@Override
public void listAuthors(BookRequest request, StreamObserver<Author> responseObserver) {
    // Gửi nhiều authors
    for (Author author : getAuthorsForBook(request.getBookId())) {
        responseObserver.onNext(author);
    }
    responseObserver.onCompleted();
}
```

**Client implementation**:

### 13.3. Ví dụ Client Streaming RPC

**Schema.proto**:
```proto
rpc CreateAuthors(stream Author) returns (CreateAuthorsResponse) {}
```

**Server implementation**:
```java
@Override
public StreamObserver<Author> createAuthors(StreamObserver<CreateAuthorsResponse> responseObserver) {
    return new StreamObserver<Author>() {
        private List<Author> authors = new ArrayList<>();
        
        @Override
        public void onNext(Author author) {
            authors.add(author);
        }
        
        @Override
        public void onError(Throwable t) {
            // Xử lý lỗi
        }
        
        @Override
        public void onCompleted() {
            // Lưu tất cả authors đã nhận được và trả về response
            CreateAuthorsResponse response = CreateAuthorsResponse.newBuilder()
                    .setCount(authors.size())
                    .build();
                    
            responseObserver.onNext(response);
            responseObserver.onCompleted();
        }
    };
}
```

**Client implementation**:
```java
StreamObserver<CreateAuthorsResponse> responseObserver = new StreamObserver<CreateAuthorsResponse>() {
    @Override
    public void onNext(CreateAuthorsResponse response) {
        System.out.println("Created " + response.getCount() + " authors");

    @Override
    public void onError(Throwable t) {
        System.err.println("Error: " + t.getMessage());
    }
    
    @Override
    public void onCompleted() {
        System.out.println("Completed");
    }
};

StreamObserver<Author> requestObserver = asyncStub.createAuthors(responseObserver);
```

### 13.4. Ví dụ Bidirectional Streaming RPC

**Schema.proto**:
```proto
rpc ProcessAuthors(stream Author) returns (stream AuthorProcessingResult) {}
```

**Server implementation**:
```java
@Override
public StreamObserver<Author> processAuthors(StreamObserver<AuthorProcessingResult> responseObserver) {
    return new StreamObserver<Author>() {
        @Override
        public void onNext(Author author) {
            // Xử lý mỗi author và trả về kết quả ngay lập tức
            AuthorProcessingResult result = processAuthor(author);
            responseObserver.onNext(result);
        }
        
        @Override
        public void onError(Throwable t) {
            // Xử lý lỗi
        }
        
        @Override
        public void onCompleted() {
            // Khi client hoàn thành việc gửi dữ liệu
            responseObserver.onCompleted();
        }
    };
}
```

**Client implementation**:
```java
StreamObserver<AuthorProcessingResult> responseObserver = new StreamObserver<AuthorProcessingResult>() {
    @Override
    public void onNext(AuthorProcessingResult result) {
        System.out.println("Received result for author: " + result.getAuthorId());
    }
    
    @Override
    public void onError(Throwable t) {
        System.err.println("Error: " + t.getMessage());
    }
    
    @Override
    public void onCompleted() {
        System.out.println("Server completed sending results");
    }
};

StreamObserver<Author> requestObserver = asyncStub.processAuthors(responseObserver);

// Gửi nhiều authors và nhận kết quả cho mỗi author
for (Author author : authorsList) {
    requestObserver.onNext(author);
    Thread.sleep(500); // Đợi một chút để xem kết quả
}

requestObserver.onCompleted();
```

## 14. Best Practices và Optimization

### 14.1. Hiệu suất

1. **Reuse gRPC channels**: Channel tạo ra nhiều kết nối TCP persistent, nên tái sử dụng chúng.
   ```java
   // Đúng - tạo một channel và sử dụng lại
   ManagedChannel channel = ManagedChannelBuilder.forAddress(host, port).build();
   Stub stub1 = ServiceGrpc.newStub(channel);
   Stub stub2 = ServiceGrpc.newStub(channel);
   ```

2. **Batching requests**: Gom nhóm các request nhỏ thành một request lớn.
   ```java
   // Thay vì gọi N lần với 1 item
   for (Item item : items) {
       saveItem(item);
   }
   
   // Gọi 1 lần với N items
   saveItems(items);
   ```

3. **Sử dụng streaming thay vì unary** cho dữ liệu lớn.

4. **Compression**: Bật compression để giảm kích thước dữ liệu.
   ```java
   ManagedChannel channel = ManagedChannelBuilder.forAddress(host, port)
           .enableFullStreamDecompression()
           .build();
   ```

### 14.2. Reliability

1. **Timeout**: Luôn đặt timeout cho mọi RPC call.
   ```java
   stub.withDeadlineAfter(5, TimeUnit.SECONDS).myMethod(request);
   ```

2. **Retry**: Cấu hình retry cho các lỗi tạm thời.

3. **Circuit Breaking**: Ngăn chặn gọi đến các service không khả dụng.
   ```java
   // Sử dụng thư viện resilience4j
   CircuitBreaker circuitBreaker = CircuitBreaker.ofDefaults("backendService");
   Supplier<Response> decoratedSupplier = CircuitBreaker
           .decorateSupplier(circuitBreaker, () -> stub.myMethod(request));
   ```

### 14.3. Security

1. **TLS/SSL**: Luôn bật TLS/SSL trong môi trường production.

2. **Authentication**: Sử dụng interceptor để thêm token vào mọi request.

3. **Authorization**: Kiểm tra quyền truy cập ở server.

### 14.4. Monitoring

1. **Logging**: Log tất cả các gRPC calls và errors.

2. **Metrics**: Thu thập metrics như số lượng calls, latency, error rates.

3. **Tracing**: Sử dụng distributed tracing để theo dõi request qua nhiều services.
   ```java
   // Sử dụng OpenTelemetry
   Tracer tracer = openTelemetry.getTracer("my-service");
   Span span = tracer.spanBuilder("grpc-call").startSpan();
   try (Scope scope = span.makeCurrent()) {
       // Gọi gRPC
       stub.myMethod(request);
   } finally {
       span.end();
   }
   ```

### 14.5. Versioning

1. **Package versioning**: Thêm phiên bản vào tên package.
   ```proto
   package com.didan.v1;
   ```

2. **Field evolution**: Thêm trường mới với reserved field numbers.

3. **Backward compatibility**: Luôn bảo đảm backward compatibility khi thay đổi API.

## 17. Sử dụng Proxyless Service Mesh với gRPC và Spring Boot (chỉ trong môi trường Kubernetes)
Trong môi trường Kubernetes, việc sử dụng Service Mesh giúp quản lý giao tiếp giữa các microservices trở nên dễ dàng hơn. Proxyless Service Mesh như gRPC với Spring Boot có thể được tích hợp thông qua các công cụ như Istio hoặc Linkerd.

Mặc định chế độ kết nối là Sidecar.
 
Giải thích Architecture

### 17.1. File Bootstrap config chứa địa chỉ của Control Plane (Istio) - nơi gRPC client sẽ kết nối để lấy thông tin service discovery.

- Mục đích: Cho gRPC client biết kết nối đến đâu để lấy thông tin service discovery
- Địa chỉ: istiod.istio-system.svc.cluster.local:15010 (Istio control plane)

> XdsBootstrapConfig.java
```java
package com.didan.testperformance.first.config.grpc;

import lombok.extern.slf4j.Slf4j;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.io.Resource;

import javax.annotation.PostConstruct;
import java.io.IOException;
import java.nio.charset.StandardCharsets;

@Slf4j
@Configuration
public class XdsBootstrapConfig {

    @Value("${grpc.xds.bootstrap-config-path}")
    private Resource bootstrapConfigResource;

    @PostConstruct
    public void initializeXdsBootstrap() {
        try {
            String bootstrapConfig = bootstrapConfigResource.getContentAsString(StandardCharsets.UTF_8);
            log.info("Setting xDS bootstrap configuration");

            // Set the system property that gRPC uses to find the bootstrap config
            System.setProperty("io.grpc.xds.bootstrapConfig", bootstrapConfig);

            log.info("xDS bootstrap configuration set successfully");
        } catch (IOException e) {
            log.error("Failed to load xDS bootstrap configuration", e);
            throw new RuntimeException("Failed to initialize xDS bootstrap configuration", e);
        }
    }
}
```
- Vai trò: Đọc file bootstrap config và thiết lập cấu hình xDS cho gRPC client
- Cách hoạt động: Đọc file từ đường dẫn cấu hình và đặt vào system property

> XdsConfiguration.java
```java
package com.didan.testperformance.first.config.grpc;

import io.grpc.LoadBalancerRegistry;
import io.grpc.NameResolverRegistry;
import io.grpc.xds.WeightedRoundRobinLoadBalancerProvider;
import io.grpc.xds.XdsNameResolverProvider;
import jakarta.annotation.PostConstruct;
import org.springframework.context.annotation.Configuration;

@Configuration
public class XdsConfiguration {

  @PostConstruct
  public void registerXdsResolver() {
    NameResolverRegistry.getDefaultRegistry().register(new XdsNameResolverProvider());
    LoadBalancerRegistry.getDefaultRegistry().register(new WeightedRoundRobinLoadBalancerProvider());
  }
}
```
- Vai trò: Đăng ký xDS name resolver và load balancer vào gRPC client
- Mục đích: Cho phép gRPC client sử dụng xDS để resolve tên service và load balance
- XdsNameResolverProvider: Giúp gRPC client hiểu cách resolve tên service qua xDS
- WeightedRoundRobinLoadBalancerProvider: Cung cấp thuật toán load balancing theo trọng số
- Đăng ký: Được thực hiện trong phương thức annotated với @PostConstruct để đảm bảo nó được gọi sau khi bean được khởi tạo

### 17.2. ProxylessChannelGrpc sẽ sử dụng xDS target để nói cho gRPC biết rằng nó cần tìm service thông qua xDS discovery, không phải kết nối trực tiếp.
> ProxylessChannelGrpc.java
```java
package com.didan.testperformance.first.config.grpc;

import com.didan.testperformance.first.entity.RequestServiceGrpc;
import io.grpc.CallOptions;
import io.grpc.Channel;
import io.grpc.ClientCall;
import io.grpc.ClientInterceptor;
import io.grpc.ManagedChannelBuilder;
import io.grpc.MethodDescriptor;
import java.util.concurrent.Executor;
import java.util.concurrent.TimeUnit;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Slf4j
@Configuration
@RequiredArgsConstructor
public class ProxylessChannelGrpc {

  @Value("${grpc.xds.service-name}")
  private String xdsServiceName;
  @Value("${grpc.xds.load-balancing-policy}")
  private String loadBalancingPolicy;

  public static final String SECOND_SERVICE = "seconds-service";
  public static final String GZIP_COMPRESSION = "gzip";
  public static final String XDS_SCHEME = "xds:///";
  private final GrpcInterceptor grpcInterceptor;
  @Qualifier("ioExecutor")
  private final Executor executor;

  @Bean
  public RequestServiceGrpc.RequestServiceBlockingStub proxylessSecondServiceBlockingStub() {
    Channel channel = createChannel();
    return RequestServiceGrpc.newBlockingStub(channel);
  }

  private Channel createChannel() {
    String target = buildXdsTarget();
    log.info("Creating xDS proxyless channel to second gRPC server with target: {}", target);
    return ManagedChannelBuilder.forTarget(target)  // Sử dụng forTarget() cho xDS, không phải forAddress()
        .executor(executor)
        .intercept(grpcInterceptor)
        .intercept(gzipInterceptor())
        .defaultLoadBalancingPolicy(loadBalancingPolicy)
        .keepAliveTime(30L, TimeUnit.SECONDS)
        .keepAliveWithoutCalls(true)
        .keepAliveTimeout(10L, TimeUnit.SECONDS)
        .disableRetry()
        .usePlaintext()
        .build();
  }

  private String buildXdsTarget() {
    // Đây là tên service trong Kubernetes, không phải địa chỉ IP/port cụ thể
    // xDS sẽ resolve tên này thành các endpoint thực tế
    return String.format("%s%s", XDS_SCHEME, xdsServiceName);
  }

  private ClientInterceptor gzipInterceptor() {
    return new ClientInterceptor() {
      @Override
      public <Q, P> ClientCall<Q, P> interceptCall(MethodDescriptor<Q, P> methodDescriptor,
          CallOptions callOptions, Channel channel) {
        return channel.newCall(methodDescriptor, callOptions.withCompression(GZIP_COMPRESSION));
      }
    };
  }
}
```
- Vai trò: Định nghĩa target service mà client muốn kết nối đến
- Không phải địa chỉ IP/port: Đây là tên logic của service
- xDS sẽ resolve: Tên này thành các endpoint thực tế

> application.yml
```yaml
grpc:
  xds:
    service-name: localhost # Tên service trong Kubernetes mà gRPC client muốn kết nối đến
    load-balancing-policy: round_robin # Chính sách load balancing
    bootstrap-config-path: classpath:grpc-bootstrap.json # Đường dẫn đến file bootstrap config
```

### 17.3. Flow hoạt động
1. gRPC Client khởi tạo với target: "xds:///second-service"
                    ↓
2. gRPC đọc bootstrap config → kết nối đến Istio (istiod:15010)
                    ↓
3. gRPC hỏi Istio: "second-service ở đâu?"
                    ↓
4. Istio trả về danh sách endpoints: 
   - 10.244.1.15:9090
   - 10.244.1.16:9090
   - 10.244.1.17:9090
                    ↓
5. gRPC tự load balance giữa các endpoints này (bypassing sidecar proxy)

## 18. Kết luận

gRPC là một công nghệ hiện đại và mạnh mẽ cho phép triển khai các API hiệu suất cao trong môi trường phân tán. Với sự hỗ trợ mạnh mẽ từ Spring Boot, việc tích hợp gRPC vào các ứng dụng Java trở nên dễ dàng và hiệu quả.

Ưu điểm của việc sử dụng gRPC trong Spring Boot:
- Hiệu suất cao với HTTP/2 và Protocol Buffers
- Định nghĩa API rõ ràng với contract-first approach
- Hỗ trợ streaming hai chiều
- Tích hợp dễ dàng với Spring Boot ecosystem

Một số thách thức:
- Đường cong học tập dốc hơn so với REST
- Khả năng interoperability với web browsers hạn chế
- Tooling chưa phổ biến như REST

Tuy nhiên, với những ưu điểm vượt trội, gRPC là một lựa chọn tuyệt vời cho giao tiếp giữa các services trong các hệ thống microservices hiện đại.
